# Episode 04 — snapshot v2 and v1 migration

Add `import_snapshot` (`name`,`data`). Legacy v1 data is `{tick,entities}` with
movers only and an empty queue. v2 is `{version:2,tick,entities,pending}`;
entities explicitly contain mover/follower kind and precise fields, and
pending entries are `{at,sequence,order,command}`. All arrays are canonically
sorted; `order` is unique. Validate all shape, ranges, past-at values,
duplicates, and references before storing, atomically. Invalid version yields
`snapshot_version`; other invalid data uses existing shape/value/entity errors.

Import succeeds with `import:<name>`, stores only the named snapshot, and does
not change the live world. `load` remains named. From this episode onward
response snapshots supersede the old shape with `{"name":name,"data":<v2>}`.
Preserve all
prior behavior and checked arithmetic.

The exact v2 entity alternatives are
`{kind:"mover",id,x,velocity}` and
`{kind:"follower",id,x,velocity:0,target:<id-or-null>}`.
Legacy entities have exactly the seed entity keys. Tick is non-negative signed
64-bit; imported x/velocity are signed 64-bit (not the narrower spawn-input
bounds). Followers must have velocity zero and targets must name an imported
entity or be null; a self-target is invalid. Missing targets are `missing_entity`.
Unknown entity kinds, duplicate entity IDs, invalid ordering values or self
references are `invalid_value`. Shapes/values are checked before relationships.
No movement occurs on import.

v2 `pending` is required. Each entry has the four specified fields: at must be
greater than the imported tick and at most 1,000,000; sequence/order are
non-negative signed 64-bit; order values must be unique. Validate commands as
at enqueue, without checking current entity existence. Canonical output pending
order is (at, sequence, order); entity order is ordinal id. Input array order
need not be canonical. From this episode, every new enqueue uses one plus the
greatest currently pending order, or zero when the pending queue is empty. This
fixes the exposed ordinal representation without preserving drained history.
If that greatest order is Int64.MaxValue, the enqueue fails atomically with
`overflow`. Importing or loading an otherwise valid queue with that order does
not itself overflow; it does not need to compute a new admission ordinal.

Legacy data has exactly tick/entities and implies empty pending work; explicit
unsupported version values produce `snapshot_version`. Import overwrites the
named snapshot. Save/load continues to deep-copy all current-world state, not
the named snapshot registry or accumulated effect/error logs. Previously created
snapshots are rendered in the current response schema, including legacy imports.
The request protocol and response top-level version remain 1.

`data` must be an object. When a version field is present it must be the JSON
integer literal 2; any other value/type is `snapshot_version`. Otherwise the
legacy shape applies. Extra/missing keys or wrong field types use
`invalid_shape`; numeric-literal, range and ID-domain violations use
`invalid_value`, as in the seed contract. Newly declared optional v2 fields
from later public requirements are the only additions to these exact shapes.

## Public example

Input: `{"version":1,"operations":[{"op":"import_snapshot","name":"old","data":{"tick":3,"entities":[{"id":"a","x":5,"velocity":2}]}},{"op":"load","name":"old"}]}`

Output: `{"version":1,"state":{"tick":3,"entities":[{"id":"a","x":5,"velocity":2}]},"effects":["import:old","load:old"],"errors":[],"snapshots":[{"name":"old","data":{"version":2,"tick":3,"entities":[{"kind":"mover","id":"a","x":5,"velocity":2}],"pending":[]}}]}`
