## Sharpened value and how it would be tested

The revised proposal asks:

> Does prospective responsibility-and-coordination analysis yield better package choices than predeclared source-size and API-fit heuristics for specified maintenance changes performed by a coding agent?

The user of the result is a maintainer choosing a starting package for a declared change profile. The output is a recommendation for A, B or abstention, with explicit risks to applicable behavior. It is not an estimate of which changes an organization will receive next.

The proposal now specifies the following comparison:

1. Before A0 witnesses, record the architectural recommendation, simple rules, predicted obligations and a possible disconfirmation. Size uses the initial permitted source bundle, not the later patch. The API rule must describe actual facilities and how conflicting advantages are adjudicated.
2. Before candidate outcomes, freeze a recommendation for each chain and each heuristic. Both packages already run in the proposed paired blocks; evaluating their fixed recommendations adds no dispatches.
3. Use **final-episode joint behavioral completion** as the proposed decision endpoint. Compare the outcomes of the packages selected by each rule within a block. Retain every earlier regression, persistent failure, recovery and supersession separately. Ending successfully after recovery and succeeding at every episode are distinct outcomes.
4. Report paired differences, uncertainty, missingness bounds and recommendation coverage. Same-package choices cannot demonstrate incremental advantage. If a heuristic abstains, an architectural recommendation adds coverage, but has not thereby beaten an unspecified default choice.
5. Keep all contrary outcomes. A1 must still fix the meaningful difference, interval procedure and finite sample justification. No claim of calibrated forecasts or population-wide decision improvement follows from two deliberately selected chains.

This gives useful implications for positive, negative and mixed findings:

| Observation | Supported implication |
| --- | --- |
| Architectural choice does better than a disagreeing heuristic on the chosen profile | Local evidence for following that recommendation under the studied policy, subject to uncertainty |
| Both recommend the same package | No observed incremental choice value; explanatory annotations may still generate later hypotheses |
| Architectural choice does worse | A documented failure of the recommendation; revise its scope after reporting, without replacing the unfavorable task |
| Package advantage differs by change profile | Package choice should be conditional on those demands; a single overall ranking conceals the difference |
| Advantage changes between inherited and reference states | The recommendation depends on the starting-state policy; the contrast does not isolate architectural damage |
| A0 reveals an API mismatch or unusable observation | Redirect before spending candidate calls on an uninformative comparison |

Two limits matter for the claimed benefit. First, the proposed no-feedback/no-repair workflow supports a restrictive-policy robustness claim. Relevance to interactive development is a separate empirical question. Second, recording analysis effort would help a later economic study, but this proposal does not measure human analysis cost or adoption, so it cannot claim labor savings or positive return on investment.

## Methodology audit and remaining evidence

A01 adds a further warning: difficulty within a single component can be justified by its domain or technical demands. The revised source cards and validity table now record this rival explicitly, so low coordination cannot simply be equated with easy maintenance.

The existing proposal already protects several essential distinctions: prospective cards versus post hoc explanation; behavioral success versus style; source-package assignment versus later architectural drift; inherited failures versus new regressions; and candidate failure versus infrastructure missingness. Accepted requirements accompany the actual safe predecessor; hidden results never control repairs or sample extension. RQ3 includes both packages and all assigned histories at declared sentinel positions, avoiding success-only predecessor selection.

[Runeson and Höst's methods guidance](https://doi.org/10.1007/s10664-008-9102-8) supports explicit case/unit boundaries, traceable protocols, rival explanations and appropriate validity reporting. Its natural-context definition also cautions against labeling a controlled repository experiment a naturalistic case study. The guidance is now fully read; the formal protocol is still unfinished. It does not require recruiting a random sample of architects to inspect this no-human A0 case.

| Stage | Evidence or decision still needed | Why it matters |
| --- | --- | --- |
| Before first A0 witness, if A0 is authorized | Source-grounded recommendation and size/API comparator rules, with a clear disagreement or additional falsifiable prediction | Avoid defining the rival after seeing which implementation is convenient. An abstention is not a fabricated baseline loss. |
| During bounded A0 | Both pinned baselines running, a credible application-level contrast, common behavioral observations, meaningful faults and legitimate alternatives | Source inspection alone has not established runtime feasibility, comparability or oracle validity. A0 exists to test these conditions. |
| At A0 disposition | Record whether witness construction exposed or changed the prediction and whether the case discriminates beyond API/size | Trusted construction is not independent confirmation of a predictive method. Selection for disagreement creates a diagnostic case. |
| Before candidate protocol adoption | Exact chains, endpoint/weights, meaningful difference, comparator/abstention rules, sentinels, model, budgets, pairing and uncertainty procedure | Prevent post-outcome analysis choice and pseudoreplication. Repetitions estimate variability on the chosen cases, not additional architectures or independent change families. |
| Before candidate execution | Validated observations and references, full finite allocation including sentinels, actual controller/sandbox/accounting checks and separate authorization | A paper proposal and document CI do not supply apparatus or scientific execution evidence. |

The proposed package contrast cannot separate architecture, API, physics and familiarity with only these two implementations. Explicit rivals can expose weak explanations; they do not statistically remove those differences. Likewise, a better recommendation outcome does not prove that responsibility organization caused the advantage.
