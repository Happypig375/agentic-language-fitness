## What this pass adds beyond the preceding review

### R1 — Architecture predictions need rivals and prospective evidence

The previous proposal already asked for favorable and unfavorable scenarios. It did not sufficiently specify when the prediction is recorded or what makes it more informative than a post-hoc explanation of a package score.

The revised A0 requires a prediction card before each reference witness: requirement, current state/responsibility owners, coordination path, expected advantage/tie/uncertainty, adverse case, rival explanation and observable disconfirmation. Record refinements separately from original predictions. Reference authors can learn while constructing; that learning is not independent confirmation of their original theory.

A trivial source-size preference or one package's missing API may explain a result. Explicitly compare those rivals with the organizational account. Do not force one win for each package or add a large prediction model to two chains. The decision value is which obligations and responsibilities become hard, not whether a favored label tops a table.

**Consequence:** A0 acceptance now needs a credible discriminating witness, not only successful execution of two baselines.

### R2 — Recover ChainSWE as a close control/interface predecessor

Primary ChainSWE v1 methods already include oracle prior fixes, fresh sequential state, persistent history and subagent interfaces. Earlier ALF discussions knew the chain benchmark, but the current proposal's central comparison did not make that full overlap clear.

Those modes are methodological resources. They do not automatically establish a perfectly isolated memory effect, and neither copying their name nor adding a subagent is a new contribution. The updated synthesis restores them and makes prospective architectural predictions, not chaining/control novelty, the center of the proposed value.

**Consequence:** future predecessor or repair-interface claims must describe the actual added intervention beyond known controls.

### R3 — Select the claim/control pair before A1, not after results

The preceding review correctly distinguished no-reset robustness from latent maintainability. This pass makes the choice operational. Without another starting-state condition, the current one-shot/no-repair chain measures restrictive-policy robustness, including initial output mistakes and overt broken code.

For the stronger inherited-state claim, predeclare selected later sentinel tasks and run both packages from validated reference predecessors as well as actual inherited states, regardless of whether the inherited history is successful. Report inherited and reference package contrasts and their difference with missingness and cost. This is a starting-state-policy contrast, not a pure architectural-damage variable or mediation percentage.

The control is recommended when the paper's intended claim includes downstream maintainability beyond immediate failure persistence. A narrower case remains legitimate. A1 must select the scope before collecting data, and control requests belong inside a revised allocation rather than being silently added to the 192-generation proposal.

**Consequence:** no success filtering, outcome-selected sentinels or promotion of a minimal design to a stronger claim after a favorable result.

### R4 — No repair is not protected repair, and useful feedback is not noise

The no-tools/no-feedback policy is retained as proposed, not silently replaced. It removes the benefits of repair as well as its transcript. It therefore cannot establish that insulation of low-level work protects a planner.

Type-Error Ablation's selected v2 methods and limitations supply relevant contrary evidence: detailed active error information can be helpful in its restricted setting. Complexity Trap's current v3 supplies a simple history-management baseline and shows why policy/tuning scope matters. The project now separates useful current diagnostics, resolved historical output, obsolete source and irrelevant repetition. A result about one is not evidence about all four.

A later fixed-source handoff could supply the same corrected source, next task and concise resolution facts to two fresh contexts, adding authentic resolved repair history to only one. That directly tests the extra history's presentation, but not native persistent hidden state, the value of repair itself or worker-generated code quality. It remains a separate unallocated option, not another compulsory phase.

**Consequence:** simple masking/history policies precede any novelty claim about workers; actual delegation must retain current evidence and report planner, worker and total system costs.

Match requirements and documentation information; do not artificially equalize the needed coordination or patch size, which may be the benefit under test.

**Consequence:** a portable architectural mechanism is a later claim requiring appropriate additional evidence, not a automatic interpretation of a package result.
