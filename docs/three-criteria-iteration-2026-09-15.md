## V1 — Beating a weak heuristic can add no scenario-sensitive value

The previous proposal explicitly compared the recommendation with size/API rules. It could therefore appear successful even when the analysis always recommends the same generally stronger package.

**Synthetic example, not ALF data:** suppose A has success probability 0.8 and B 0.5 for each of two profiles. A detailed rule always choosing A beats a size rule choosing B by 0.3. It improves on always-A by exactly zero. The result establishes a package difference, not a need for profile analysis.

A different synthetic panel makes A better on profile 1 and B better on profile 2, with probabilities (0.9,0.4) and (0.4,0.9). Correct profile-sensitive choices have value 0.9 while either constant has value 0.65. That is the kind of incremental choice result the stronger study is trying to detect, without assuming it exists in Nu.

**Changed:** always-A and always-B, a development-selected default, and frozen size/API policies enter the comparator panel. The best fixed package discovered on evaluation outcomes is labelled an optimistic descriptive reference. An equal-information, equal-budget ordinary review is required for claims about the structured analysis procedure's extra benefit; otherwise the conclusion remains advice versus the specified simple rules.

## V2 — Define the deployable decision and include advice cost

Two available implementations under known planned changes define a plausible adoption choice. Recommending an architecture for an entirely unknown future, generating both implementations from scratch, migrating an existing application and choosing an agent scaffold are different actions. They have different costs and available information.

**Changed:** a decision contract states beneficiary, action, initial evidence, known profile, target policy, fallback and useful outcome. Advice burden is recorded separately from candidate and controller cost. Abstention has a predeclared fallback or bounded value; hard profiles cannot disappear from the main score. A minimum useful effect and permissible failure/resource trade-offs must be justified before data. No ROI claim is inferred from token savings alone.

The deliverable could be an auditable procedure and evidence showing when a default suffices, not necessarily a new automated recommender. A well-bounded negative result is useful; an imprecise non-result is not evidence of no value.

## S1 — Frozen predictions on tuned scenarios are not an independent method test

A0 reference witnesses expose the authors to the implementation trade-offs. Freezing a prediction after that development and later sampling the model repeatedly does not make the scenario independent of method construction. The previous proposal already acknowledged this limitation; this revision makes the stronger design alternative concrete rather than leaving it as a caveat.

**Changed:** A0 remains development. The procedure is frozen before it sees new evaluation profiles, and its per-profile choice is frozen before reference solutions/candidate outcomes. Hold out profiles/chains, not nearby episodes sharing the same story. Record actual author/selector knowledge; seek separate construction and challenge roles without claiming nonexistent independence.

The selector may receive a held-out profile as its decision input. It may not use that profile's solution/outcomes to tune the procedure. The amount of future requirement detail supplied must match the stated adoption scenario. Without a credible split, report a local frozen-advice case, not predictive transfer.

## S2 — Two holdouts answer different validity questions

A hidden behavioral evaluator prevents the implementation agent from optimizing directly against final examples. It does not protect the package-selection procedure from evaluation-profile leakage. Conversely, withholding profiles during method development does not prevent a controller leaking hidden tests through repair requests.

**Changed:** profile-level development/evaluation and candidate development/final-test boundaries are separately required. References and scoring details remain outside the selector's decision evidence and candidate authority as applicable. Ordinary review must not receive less information just to make the structured method win. Candidate-visible maps would be an implementation-support treatment, not passive observation of a choice rule.

## S3 — Explicit policy-value arithmetic, shared outcomes and uncertainty

All candidate package outcomes are collected under a fixed policy. Several predeclared selectors can therefore be scored from the same panel, with no additional candidate generations. The choices must be made without outcomes; selecting the successful package per replicate is an oracle, not advice.

**Changed:** the proposal defines weighted paired value differences, primary/secondary comparator hierarchy, fixed fallbacks and all-profile reporting. When both policies select the same package, their contrast is exactly zero. If the underlying outcome is missing, the individual values may remain unknown but that shared difference still cancels. Missing bounds must preserve this dependence.

Repeated blocks estimate stochastic variability for chosen profiles. They do not create new architectural cases or change families. New profiles support procedural transfer; new independently authored package families support portability. No large mixed-effects model, power claim or universal ranking follows from two chains. Outcome-driven sample extension remains prohibited.

## S4 — No-repair results need a beneficiary who actually uses that policy

The currently proposed one-submission/no-repair chain is retained, not silently changed. It is a clean restrictive policy but can be dominated by ordinary generation failures and inherited noncompiling source. It does not preserve repair benefits while removing planner history.

**Changed:** before the practically oriented selection study is allocated, A1 must either justify that policy for the beneficiary and narrow the claim, or separately specify a bounded hygienic development-feedback policy. Existing E3a controls can be reused; no worker architecture is required. Reference-predecessor sentinels remain the control for a starting-state question, not a substitute for interactive repair or a causal measure of architecture damage.

This is a relevance gate, not permission to launch a new treatment or rerun E. A repair-history or actual delegation question remains conditional later work.

## S5 — Endpoint choice changes the implication

Terminal build-plus-behavioral completion is retained as the proposed primary endpoint. It measures success by the end, not uninterrupted operation or absence of earlier regressions. Every-episode obligation transitions remain visible. The definition cannot change after seeing which package wins.

**Changed:** a continuous-reliability beneficiary must choose that utility before data rather than infer it from terminal success. Architecture annotations do not overrule behavior, and candidate-induced versus infrastructure-unobserved outcomes retain their distinct classifications. Correct reorganization is not a treatment violation merely because style changed.
