## Mechanism and language development

The pattern deliberately restricts part of a game loop so query processing can share computation. State is unchanged during the query phase; temporary effects accumulate contributions and reset between steps. The update phase combines completed effects with old state. If an attribute plays both roles, it needs separate fields. The authors require order-independent combination: mathematical sum is their associative/commutative example. This is not a guarantee of bitwise reproducibility for arbitrary machine arithmetic.

The later SGL account separates data files, which declare object fields and update expressions, from scripts, which describe per-object query behavior. Scripts can access only fields exposed through data files; other host-engine fields may remain outside the language. Supported values include numbers, declared object types and unordered sets. Built-in effect operations include sum, min, max, average, set union and priority selection. An object priority or argmin/argmax selects one result, with the built-in opaque priority resolving ties. The paper describes aggregate average, not a proof that a naive pairwise average is associative.

Effects are write-only during a query. Local `let` variables are immutable. An `accum` loop has two blocks: the first emits contributions while visiting an unordered collection; after the combination completes, the second may read the immutable result. Figure4 chains a minimum-health aggregate with a search for an eligible unit at that health. The authors say a query optimizer can combine these passes, while an argmin expresses the task more directly. These language constraints expose common work and prevent reading partial effect accumulation; the performance claim is not about arbitrary imperative code being automatically optimized.

The host invokes one query/update step and can perform additional operations before the next invocation. The pattern itself permits unrestricted postprocessing, including collision resolution. The authors warn that this escape hatch can dominate cost. Section6 distinguishes the earlier prototype's single object type and SQL-dependent iteration from the more advanced language described here. Its performance graph nevertheless reuses the earlier prototype's results; it does not separately measure the benefit of the revised syntax or a general automatic compiler.

## Positive timing evidence and the disputed legend

Figure5 repeats the S223 scan/index comparison: elapsed processing time for **500 simulation steps**, with aggregate-index construction and maintenance included. The favorable order-of-magnitude scaling result is retained under that workload. The paper's 100ms simulation-step discussion is a throughput interpretation of this aggregate time, not a measured rendered-frame latency distribution. The repeated plot is not a new empirical case.

Figure6 adds a healer-only comparison in the **same prototype**, beginning with wounded allies and letting them recover over roughly 500 ticks. The proposed strategies are aggregate indexing and pruning healthy allies before scanning. The text says indexing is preferable when many units are wounded, whereas pruning becomes preferable as few wounded units remain. This is a consequential qualification of an unconditional indexing advantage.

However, **the printed legend reverses that textual interpretation**. On PDF page6, the blue curve labeled *Indexing* falls from about 0.32 seconds to near zero; the red curve labeled *Pruning* stays around 0.05 seconds. The two cross near tick180. The prose instead describes the falling curve as pruning and the roughly constant cost as indexing. These are approximate visual observations, not digitized raw measurements. Without a corrected edition or data, retain the observed crossover and the authors' workload-dependent argument, but do not assign those plotted costs to an algorithm as a verified fact. Nor does this graph demonstrate a measured adaptive optimizer: it compares the alternatives; dynamic switching and its overhead are discussed as the desired optimization.

Section4.3 explicitly says **pipelining and parallelization have not been applied to SGL** in this work. The paper explains why on-demand relational evaluation could reduce intermediate storage and why isolated query contributions admit parallel execution. These are mechanism/extension arguments. They are not measured SGL memory savings, GPU speedups or multicore scaling. Claims about developer focus, saved engineering time and richer gameplay likewise have no human or player outcome study here.

## Semantic design and integration obligations

Delaying state changes is a design obligation. Effects that must not stack need a selection rule rather than independent additions. For mutually exclusive enhancements, the paper proposes one selected effect object carrying type, strength and priority. This simplifies the combination rule but does not discover the intended game rule automatically.

The loot example makes the ownership constraint concrete. If each loot object has one owner, put the owner effect on the loot object and let its priority rule select one claimant. Putting independent acquisition effects on each player would not enforce uniqueness when players execute against the same old state. Inventory changes must then follow the selected owner in an update or subsequent step. This is useful positive design guidance: common-state evaluation still requires the right location and meaning of constraints.

The query fragment excludes arbitrary recursion/transitive graph search, so A* pathfinding cannot simply be written as an unrestricted inner query loop. The authors discuss restructuring work across characters while iterating search steps in the host, and explicitly leave its performance advantage uncertain. Alternatively a separate pathfinding subsystem can deliver waypoint sets to steering, synchronously in postprocessing or asynchronously. The paper does not supply a protocol proving consistent asynchronous delivery, pending-work migration or external-effect replay. Integration remains part of the system's behavior and costs.
