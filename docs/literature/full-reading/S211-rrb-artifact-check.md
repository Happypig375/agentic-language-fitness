## Workload and comparator reconstruction

The reproduction script sets the three paper sizes/sample counts and `-O3 -march=native`. It does not archive measurements or fix all external dependencies. The Dockerfile clones an unpinned repository and installs then-available packages, so rebuilding that recipe today would not alone reproduce the historical environment. It was read as source only.

The append helper starts from an empty collection each timed repetition. The standard vector does not reserve N slots. The ordinary persistent variant repeatedly assigns the next value over the previous one; the transient variant retains one mutable handle. A move-based helper exists but is not registered by the paper's push file. Therefore the published append comparison is not by itself the claimed system-wide rvalue/aliasing ablation.

The ordered-update helper builds an initial persistent `v` outside timing, then times `r=v` followed by repeated assignments to `r`. The transient helper creates `v.transient()` inside the timed operation, preserving v. Intermediate r values are discarded. The standard-array helper constructs `meter.runs()` full copies outside timing and selects one for the update loop. The comparison usefully measures operation costs under these preparations, but does not include all array snapshot-creation cost or the cost of retaining every persistent result. Reclamation/peak memory and reference lifetimes are not fully characterized by these snippets.

Concat prepares one N/10-element input, then appends that same input ten times to the result. This induces repeated sharing; it is not ten independently evolving chunks. The GC transient paper registration preserves the input; a consume-both helper is present but not the registered comparison. Access traverses sequential indices or uses iteration/reduction. Random helpers exist separately; they use a fixed-seed index stream with replacement, not a random permutation. Presence of code does not turn the paper's informal random-update remarks into a reproduced result.

At this pin, paper registrations named `transient relaxed ours/...` pass `push_back_fn`, whereas their persistent relaxed counterparts pass `push_front_fn`. The source therefore does not establish distinct relaxed-tree preparation for those transient labels. This is a bounded label/construction discrepancy in the inspected pin, not a demonstrated defect in the exact published execution. The selected results and overall batching mechanism remain separate evidence.

## Printed notation versus implementation

The p.8 prose's within-leaf index `floor(i/Ml)` conflicts with its own Figure4: i=9 and Ml=2 require slot1. Listing3.1 and the actual leaf-position methods use masking, equivalent to `i mod Ml`. Equation2's real-valued log formula would become negative for sufficiently large T; the dated implementation instead divides integer usable node space by element size and maps zero to zero, giving Bl=0. These source checks resolve the intended mechanism without asserting the whole implementation correct.

Listing4.1 and AppendixA contain schematic inconsistencies (including child/slot references and dispatch details). Algorithms6.1/6.2 explicitly present operation structure and omit full recursion/base cases. They should not be executed literally or treated as proof that the library loops incorrectly. The inspected real position method selects the child by the computed slot, subtracts the preceding cumulative size and dispatches using the reduced shift. No independent implementation or runtime validation was performed.

The consequential remaining gap is the mapping from these historical workloads to retained histories and interactive runtime obligations, not a need to repair the author's library. S213/S212 and the existing collector/reuse/snapshot reconstructions supply independent alternatives; an actual Nu effect remains unmeasured.
