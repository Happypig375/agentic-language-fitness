## Live claims and mechanism

B02/B03/B04/B07/B08 concern evolving schemas, preserving identity and transferring edits without pretending that structural consistency determines intent. Baseline records high-level operations, including schema changes, in append-only histories. This distinguishes a rename/move from an observationally similar delete/recreate sequence. It also requires observing edits through its operation vocabulary; arbitrary external editors do not automatically provide these histories. Branching copies a document/history, and a common history can be synthesized for comparison. Removing the need for a separately managed repository does not remove stored history, correspondence or resource costs.

The model uses nested homogeneous lists, records, strings and numbers, with persistent field/element identifiers rather than names or list positions as identity. Types and values are presented separately, with initial values such as the empty string, empty list and `NaN`. Actual Baseline uses initial-value prototypes, including a list header. The claim that prototypes could replace types without loss of power is a conjecture. Sum types and aliases are outside this presentation; it supplies no direct test of F# union exhaustiveness or D1's assigned convention.

Figure 1 distinguishes value operations from schema operations. The latter include defining/converting types, renaming/moving fields, wrapping a value in a list/record, and selecting a list's first element or a record field. They are partial functions with preconditions. Wrapping assigns the original value a special stable element ID, `1`; this correspondence, rather than a newly inferred semantic identity, enables the later scalar/list example.

Projection takes two timelines from a common initial state and produces continuations that reach the same state. It is deliberately asymmetric: when two writes conflict, the transferred operation has priority and the other becomes a no-op. Swapping the inputs can change the result. The rules define what counts as preserving an operation's intention; the paper explicitly acknowledges that this is a policy choice without a universal objective answer. A commuting diagram therefore does not prove that a human's unstated intention was recovered.

Retraction transfers an operation backward through another operation. It can fail when the later operation depends on structure created earlier: appending to a newly created list cannot simply occur before the list exists. Transfer retracts through one branch and projects through the other. The account claims that transferring dependencies first, or synchronizing an entire branch, succeeds; that statement is within the supported abstract rules, while the implementation's rule set is explicitly incomplete. Synchronization has a direction and resolves conflicts in favor of that direction.

Diff optimization absorbs operations whose transfer does not change the other branch's state. It produces a synthetic common ancestor that may never have existed in either real history. The stated optimality concerns redundancy under these rules, not a measured globally shortest representation, runtime optimum or user-effort minimum. The paper says the roundtrip law is tested for implemented rules, but supplies no exhaustive rule inventory, test denominator or general machine-checked proof. The procedural rule implementation has become unwieldy; a declarative rule language and a smaller primitive basis are future work.

## What the cases actually establish

The ten numbered cases are analytical examples drawn from prior work, including the authors' own S73 challenge set. They are not ten independent experiments. Extract Entity was a motivating design example, so successful treatment is not held-out validation. The current revision's explicit partial/unsupported cases matter more than the older abstract's four-of-eight shorthand.

| Case / pages | Demonstrated or proposed behavior | Consequential limit |
| --- | --- | --- |
| 1, multiplicity, 10 | An old scalar write targets the original element after wrapping, even when another element is inserted before it. | Stable ID `1` fixes the correspondence; it does not infer an arbitrary user's preferred scalar/list policy. |
| 2, deletion, 10–11 | Deleting the original list member refuses backward retraction through the wrap. | Subsequent old-scalar and new-list changes become decoupled. Null/empty-string/optional-type policies are discussed as alternatives, not already supplied. |
| 3, Extract Entity, 13–14 | Split customer columns into another table, preserve row IDs, replace columns with links, and merge a duplicate row while forwarding links. | Equality of attributes is not a general proof of entity identity. The motivating toy example and simplified link model do not establish arbitrary database migration. |
| 4, nested JSON, 14 | More general Extract/Push operations can express a Sculpin restructuring example. | This is an expressiveness comparison, not measured superiority over Sculpin. |
| 5, enduring divergence, 15 | Users retain old and normalized schemas and attempt data transfer. | A new customer depends on the split and cannot transfer back; a new order gets blank customer fields. A later deduplication interaction drops an address update. A set/equivalence-class remedy is proposed for future work. |
| 6, BiDEL comparison, 15–16 | The paper compares a database-decomposition approach that avoids the illustrated anomaly. | Its one-shared-data versus independently divergent-data distinction needs the BiDEL primary method, promoted as S103; this reading does not certify the comparison. |
| 7, dependent query evolution, 16–18 | Denormalize a copy with Join, filter initially blank/nonblank values, and transfer a formula through schema changes. | A partial solution: general predicates and a full query language are missing. General pure-functional expression evolution remains conjectural. |
| 8, PRISM/Wikipedia, 18–19 | Identifies selection, copying and union operations needed for the earlier example. | These are not all implemented. Copy updates create retraction/roundtrip difficulties. |
| 9, structured document edits, 19 | An implemented regex Match extracts a group into a table column for the stated example. | It breaks the direct-manipulation goal; a more suitable parsing language is future work. |
| 10, remaining S73 challenges, 19 | Names live state type evolution, code co-evolution for structured documents and live editing of DSLs. | These require programming-language features that Baseline does not yet support. |

These cases support a mechanism for selected schema/data transformations with explicit correspondence and conflict policies. They also provide concrete adverse examples. They do not establish that all eight S73 challenges are solved, that any type change can continue safely, or that arbitrary application behavior is preserved.

## Queries, undo and implementation correspondence

The relational example adds links whose type identifies the target list and whose value identifies a row or null. Moving lists must update link paths. The actual nested, set-valued link model is more complex than Figures 7–8. Split and Join are built from more primitive operations with nontrivial transfer choices.

A formula is represented as a future timeline of operations plus a return path. It speculatively operates on a copy of the current database and returns a value. In the example, retracting Join through Split cancels the structural change while preserving a filter. Forward rewriting prepends an inverse schema operation. This is a concrete reuse of transfer machinery for the illustrated fragment, not a zero-cost proof of arbitrary code co-evolution. Query evaluation, history, rewriting and rule maintenance still require work.

Appendix B's selective undo appends compensating operations to current history. It computes an inverse relative to an earlier state, then projects subsequent changes through it so that later writes can override the undo. It is neither deletion of shared history nor reversal of an external effect. The dependency policy matters as much as whether a previous value is stored.

Appendix A explicitly separates the paper's state tombstones from the current prototype's virtual tombstone IDs stored inside insert operations. Adopting state tombstones is planned. The mathematical presentation, present implementation and next design therefore cannot be treated as one verified artifact. Figure 5(c) also prints a retained value of `2` after an append from `[1:0]`; the described append does not explain that value change. This is a local diagram discrepancy, not an independently reproduced implementation fault.

The related-work discussion explicitly distinguishes the asymmetric transfer rules from OT convergence conditions TP1/TP2 and describes ordered/central-primary replication as an alternative. Preserving divergent versions is a different objective from order-independent convergence. Claims about all CRDTs, bidirectional lenses or existing version-control systems need their primary definitions and modern counterexamples; this paper's comparisons alone do not settle them.

## Evidence, interface and supplement limits

The eleven figures include the operation model, transfer diagrams, table restructuring and two interface screenshots. The interface uses Miller columns, a split diff view, and coordinated selection computed by transferring a no-op. These are concrete design choices. No controlled usability comparison, maintenance-time estimate, task-success denominator, runtime benchmark or memory profile is supplied. Large-project history compression, caching and branch organization remain open.

Appendix D describes a scripted playable tutorial and informal author observations that users understand the intended flow. It provides no participant count, recruitment, protocol, independent scoring or comparative result. The authors report gaps when users depart from the script and state that checking every tutorial step was too costly; a history-based oracle is proposed for later work. Appendix E applies technical dimensions as a design analysis, not a validated measurement instrument or user study.

The [playable-demo URL](https://thebaseline.dev/Prog26submission/) was inaccessible through the web reader, but direct HTTPS returned its 395-byte application shell and named its JavaScript/CSS assets. Thus the URL is reachable; no interactive tutorial step, executed behavior or source equivalence was checked. The [HYTRADBOI presentation page](https://www.hytradboi.com/2025/3b6de0f0-c61c-4e70-9bae-cca5a0e5bb7b-db-usability-as-if) identifies the speaker and links slides; the video/slides were not watched/read. These explicit gaps qualify supplement coverage without undoing the complete v2 PDF reading.

## Consequences and follow-up

**Unique:** selected operation-based schema transfer, identity-aware data versioning and query rewriting have a concrete contemporary predecessor. No global priority claim follows from this reading. S86 shares authors and motivating cases with S73 and S87; it is not independent validation of their problem selection.

**Valuable:** keeping data edits usable across schema changes is a concrete capability. Its proposed simplicity, reduced cognitive burden and reduced maintenance cost remain unmeasured. Failed transfers, dropped updates, imposed conflict choices, storage costs and incomplete operation coverage are part of the value question.

**Scientifically valid:** distinguish stable identity from semantic identity, abstract rules from prototype implementation, consistent transfer from intended transfer, one-off migration from lasting divergence, and structured query fragments from arbitrary code. Preserve failed/unsupported cases and pending-work/external-state boundaries. A future oracle needs independent checks of these obligations; roundtrip tests alone do not validate all user intentions. None of this authorizes experimental construction or changes D1's assignment.

Consequential primary leads are S87 Denicek, S101 operation-based live models (also S100's predecessor), S102 Cambria and S103 BiDEL. SC28 confirms DOI metadata for S101, BiDEL, Edit lenses (`10.1145/2103656.2103715`, with a separate indexed edition `10.1145/2103621.2103715`) and PRISM (`10.14778/1453856.1453939`). S101's publisher introduction explicitly repairs an earlier omission of read-after-write dependencies; full methods remain pending. Edit lenses/PRISM, Sculpin (`10.1145/3746059.3747651`), language-based Python version control (`10.4230/LIPIcs.ECOOP.2024.9`), persistent-object evolution (`10.22152/programming-journal.org/2025/10/12`) and selective-undo/tombstone foundations remain named follow-ups, not silently completed references.
