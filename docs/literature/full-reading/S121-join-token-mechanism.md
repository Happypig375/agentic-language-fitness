## Mechanism and programmer obligations

Mogemoge is an interpreted, prototype-based object language implemented with Java and SableCC. Join tokens supplement ordinary methods. An object places a named token, its own identity and arguments into a global pool; a handler selects several token patterns, optionally tests a Boolean guard, and runs a body with the corresponding objects and values. This moves participant selection into the runtime and allows an interaction to be expressed together instead of distributed across object callbacks.

An explicit `ignition` statement starts matching. The paper specifies handler definition order, token-pattern order and older-token preference; the artifact traverses its handler registration list in order. The game author still chooses when ignition occurs relative to input, object updates and drawing. Sequential execution avoids thread interleaving; it does not establish that this chosen order implements the intended game rule.

Only one token of a given name may exist for a given originating object. Throwing another replaces it and puts the replacement at the end of that name's list. This is a current participation/state representation, not an append-only event history. Different names can coexist for one object, so mutually exclusive states require a program convention. Tokens need not match argument arity: the active interpreter path discards excess arguments and binds missing ones to nil. The otherwise read `JoinMatcher`/`FormalToken` helper has an arity test, but it is not the `TokenPool.traverse` invocation path inspected here; its existence is not evidence of an enforced arity invariant.

Ordinary matched tokens are consumed; a leading asterisk preserves a token. This expresses one-shot participation or continued availability, including an explosion affecting several objects. Object methods explicitly withdraw tokens with `dispose`; `exist` tests a token for the current receiver. Token names can expose an interaction role such as normal or invulnerable without forcing handlers to inspect all internal object state. Preserving that public role contract still requires correct updates when private behavior changes.

The shooting demonstration separates object-local behavior from five multi-object interactions among eight rules. It is constructive evidence that collisions, damage and temporary invulnerability can be written in this form. The printed rule skeleton has an R6 guard naming `s1`/`s2` despite binding `s`/`m`; it is not a verified executable specification. The artifact and full application behavior require separate treatment.

## What the dated runtime clarifies

The inspected implementation is more specific than the informal description:

- Each handler constructs an array snapshot for each formal token name. Nested loops enumerate candidate combinations; repeated names begin after the preceding same-name loop index, avoiding self-pairs and reversed duplicate combinations. New pool entries are not appended to those current arrays. Later handlers take fresh snapshots and can see new tokens during the same ignition; this is not a repeated fixed-point pass over all handlers.
- The body runs before `TokenPool` performs its automatic consumption by name and originating receiver. Consequently a body that replaces a to-be-consumed token with another of the same name and receiver has that replacement removed by subsequent cleanup. This is a static derivation from `OperationExecuter` 1206–1214 and `TokenPool` 147–156, not an executed counterexample or a claim about an unexamined release.
- Nulling an entry affects that loop's array only. For two consuming patterns of the same name, separate snapshots can retain a token removed through the other pattern. With three candidates in order, the code can consider the second token again in the first position after a successful first/second pair, since it does not recheck pool membership. This bounded source-level concern prevents treating consumption-once as a verified runtime guarantee. It was not tested by running the author program.
- For two preserved patterns with populations `n` and `m`, all candidate pairs can reach the guard: `n*m` checks, even when every guard fails. There are also snapshot, binding and removal costs. S122's informal linear description does not bound general multi-pattern matching. No speed, frame-rate or allocation measurements are inferred from this analysis.

These details matter for interpreting token lifetimes and performance; they do not erase the demonstrated expressive mechanism. A released implementation, a paper's intended semantics and verified behavioral properties are different evidence units.

## Evidence, limits and design consequences

The paper reports successful small demonstration games and no encountered performance problem at roughly a hundred handlers and a thousand tokens. It discusses a 20-frame-per-second/50-ms game budget, but supplies no controlled timing distribution, hardware-normalized comparison, human maintenance task or agent evaluation. Readability and ease claims are the authors' experience, not measured causal effects. The interpreter's reported roughly 2,400 implementation lines include about 160 grammar lines; they are not the complete integration cost of a game engine.

Token garbage collection is explicitly unfinished. The proposed policy assumes an object referenced only by tokens is dispensable; the authors say this assumption needs experience and validation. The inspected pool and token objects hold ordinary references, and demonstration methods explicitly remove objects from the display/update list and withdraw their tokens. Deleting one reference or consuming one token does not prove all subscriptions, roles and external effects are cleaned up. Larger games, naming discipline, genuine parallelism and garbage collection remain future questions in this edition.

For Nu, this is direct prior art for declarative, state-dependent multi-object interaction over ordinary objects. It relocates iteration and some participation bookkeeping, while retaining ordering, guard, role-transition, cleanup and host-library obligations. It does not provide functional-world persistence, time travel, live-state migration or an exhaustive static model of game behavior.

**Unique:** broad coordination/readability claims have a concrete predecessor; the specific Nu integration or D1 priority remains unconfirmed. **Valuable:** rule-oriented expression and small working demonstrations are credible positive evidence, with net development benefit and general runtime cost unmeasured. **Scientifically valid:** method reconstruction and static artifact checks are complete at the stated scope; behavioral equivalence, runtime defect confirmation and experimental reproduction are not established. All experimental holds remain.
