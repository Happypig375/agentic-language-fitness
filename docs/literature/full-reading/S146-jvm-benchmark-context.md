## Mechanism and comparisons

JIT compilation uses observed branch frequencies and receiver types to specialize code. An isolated benchmark that repeatedly exercises one input configuration can create a narrow profile. A library used at several application sites can instead encounter several branches, callback types and competing uses. Repeating a stable narrow measurement does not establish that its optimized machine code represents those uses.

The study runs Oracle JDK 24.0.1+9-30 and JMH 1.37 on an Intel Xeon Gold 6326, 256GB RAM, Ubuntu 22.04/kernel 5.15, with hyperthreading and turbo boost disabled. Each configuration has five JVM runs, each with five five-second warmup and five five-second measured iterations. Reported results use arithmetic means within measurements; cross-case speedup summaries use geometric means. This is one selected platform, not a random sample of runtime versions or applications. The related-work section explicitly acknowledges that performance may never settle; fixed warmup is not itself evidence of convergence.

**Hash function.** A loop-based polynomial hash is compared with a fallthrough-switch implementation for arrays of up to 32 bytes, reverting to a loop for longer arrays. Under ordinary isolated execution, the alternative's speedups over the plotted lengths range from 0.97–1.43, geometric mean 1.10. Exercising diverse lengths before measurement changes both implementations' profiles; the alternative then ranges from 0.46–1.05, geometric mean 0.91. This is a concrete reversal of the aggregate optimization decision, not merely additional variance.

The authors also record hash invocation lengths from three selected high-invocation traces each in DaCapo-Chopin and Renaissance. The six Figure 5 labels are biojava, eclipse, spring, mnemonics, par-mnemonics and movie-lens. Replaying those length sequences in a single-threaded JMH setting favors the loop baseline in all six plotted cases, consistent with the broader-input setup. This validates the direction for those selected traces. It does not preserve full application scheduling, all input contents, allocation/cache interference or whole-program runtime; the paper deliberately isolates hashing because its end-to-end share is small. The confidence-interval level and per-trace raw samples are not supplied in the plot.

**Streams.** The same implementations of 22 translated TPC-H queries are run either in isolation or after selected map/filter/collect uses exercise the Stream API. Isolated execution is faster by geometric mean 1.08, maximum 1.41 for query 6. The rounded figure shows query 20 at 1.00. Selected compilation-log inspection associates the difference with callback inlining and shared API profiles. Unlike the hashing case, this is not a ranking comparison between two implementations or a replay validation against whole applications. The pre-execution mix is a sensitivity intervention; its representativeness is not universal.

**Standard collections and identical copies.** JVM initialization exercises some standard classes before any application benchmark. Cloning their code into another package removes that prior use. CollectionBench compares HashMap/HashSet classes with those copies for contains, copy, iteration and population workloads. The geometric-mean speedups of copies are map 1.05/1.34/1.01/1.19 and set 1.06/1.16/0.99/1.26. Maxima reach 1.55 and 1.54. The set-iteration mean and minima below one qualify the text's description of consistently faster copies.

Identical algorithms with different initialization/profile histories are a strong control against attributing every measured advantage to algorithm design. The paper attributes the differences entirely to initialization, but class/package relocation also changes code identity and potentially layout; the released evidence here does not isolate every downstream compilation/layout effect independently. No copied or patched code was executed by this review.

## Implications and limits

The practical suggestions are to exercise relevant paths before measuring, compare copies under comparable conditions, or patch standard-library classes so alternatives participate in initialization. Each has limits: path coverage does not reproduce frequencies or application interference; copies can remain overly specialized; replacing standard classes requires compatibility with private contracts as well as public APIs. These are measurement choices to justify for a particular claim, not automatic permission to construct a new ISE benchmark.

[S143 CHAMP](S143-champ-immutable-collections.md) is cited as an example of collection optimization in section 7. **This paper does not rerun CHAMP.** S143's principal comparators are Scala and Clojure immutable collections, not the cloned Java standard collections evaluated here. Therefore the specific standard-library initialization asymmetry is not demonstrated for S143. Fixed operation/input profiles are a legitimate transfer concern for its microbenchmarks; its selected application evaluation remains a separate piece of evidence. The citation supplies neither a blanket refutation nor a numerical correction to CHAMP's results.

The study is constructive contrary evidence for extrapolating isolated throughput to deployed behavior. It does not measure Nu, .NET, retained history, garbage-collection tails or maintenance productivity. These remain separate B04/B06 questions. Its short bibliography also points to statistically rigorous benchmarking, non-steady performance and trace-driven measurements; the newly surfaced MapReplay publication is a concrete follow-up for operation-mix representativeness, not evidence credited before reading.

**Unique:** runtime-context confounding has established methods and predecessors; no ISE firstness follows. **Valuable:** documented ranking and magnitude changes make context a consequential measurement choice. **Scientifically valid:** full bounded case-study reconstruction supports this concern; selected traces/platform, missing exact artifact and untested Nu transfer limit generalization.
