## Mechanism and obligations

The contribution is an implementation and design account for **embedding relaxed radix-balanced vectors (ERRB)** in C++, combining unboxed elements, traversal abstractions, memory policies and transient updates. It makes persistent collections available without requiring one particular tracing collector. This is a strong predecessor for an interactive architecture built around values; its introductory claims about easier reasoning and its proposed game/database applications are motivations, not measured development outcomes.

Regular radix-balanced trees use a wide branching factor `M=2^B`, normally B=5. Index bits select a path. Relaxed nodes hold cumulative subtree sizes and admit rebalancing, enabling logarithmic concatenation/slicing without copying every element. The implementation keeps a tail outside the tree. The left-shadow and Scala-style display alternatives are discussed but not included: displays can accelerate sequential persistent updates while enlarging roots, adding reference-count traffic and complicating other operations. “Effectively constant” bounded-depth behavior does not change logarithmic asymptotic lookup into O(1).

**Embedding separates inner and leaf branching factors.** Directly storing a large value in every slot of an ordinary wide leaf would enlarge copied nodes; reducing the whole tree's branching factor would deepen lookup. ERRB instead chooses leaf bits `Bl` independently of inner bits B, aiming for similar physical leaf/inner sizes. It can retain wide inner nodes while storing fewer large objects per leaf. The actual dated source includes header sizes and a zero-input log convention; the printed sizing equation alone omits that boundary. This is representation-specific locality/copy behavior, not an intrinsic property of a functional language.

**Positions separate traversal context from tree storage.** Temporary positions carry node/size/shift information derivable along a traversal; statically dispatched visitors implement operations across regular, relaxed, full and partial nodes. Figures5–6 and the appendices explain this factorization. The author argues that removing redundant stored metadata and specializing visitors can avoid abstraction overhead. Comparisons between different implementations do not isolate a maintenance benefit from that organization, and the simplified appendix is not a complete executable implementation.

**Memory policy is part of the mechanism.** Heap allocation, reference counting, transient ownership and relaxed-node layout are compile-time choices. Separate cumulative-size arrays can be shared on updates; embedding them in one allocation changes allocation and traversal costs but loses that sharing. Some policy combinations are invalid. Atomic reference counts support sharing across threads but add traffic; unsafe counters/free lists are single-threaded alternatives. None of the serial benchmark tables establishes parallel scaling or a frame-time bound.

**Transience preserves logical versions through conditional physical mutation.** A transient can be created from a persistent root in constant time; only owned paths may be modified, otherwise they are copied. Ownership identifiers, or reference counts showing that every relevant ancestor/node is unique, authorize mutation. Freezing invalidates the transient without walking the entire tree. With reference counting, rvalue operations can reuse uniquely owned storage through a functional-looking interface. A C++ rvalue or `std::move` alone does not prove uniqueness: the paper explicitly qualifies named/moved-from aliases on p.16, and runtime ownership checks remain necessary.

Keeping an old root can prevent reuse where paths remain shared. Discarding intermediate versions permits reuse; these are different workloads. Rightmost nodes reserve capacity for appends, adding up to `M log_M n` slots and potentially hurting many small vectors. Mutable arrays, immutable small arrays and different retention policies therefore remain meaningful alternatives. Physical node sharing also says nothing about the reversibility of external effects or the immutability of objects referenced by stored values.

Confluent transience allows consuming the left input, right input or both during meld. The ownership/rebalancing bookkeeping is more complex than a simple update. The author reports little additional concat speed from general transience, because moving/rebalancing data and added branches consume the saved allocation work. The reference-counted implementation generally uses persistent concatenation plus deterministic free-list reuse, with a small tail-only mutation case; the GC/identifier implementation retains transient concat to preserve ownership tags for later updates. This is a useful bounded negative result about an optimization, alongside the positive batch-update results.

## What the evaluation measures

Tables1–4 describe a **single Intel i5-460M/4GB machine**, Debian/Linux4.9, GCC6.3, Java8u121, CPython2.7.3, Scala2.11.11 and Clojure1.8. The three sizes are **1,000 / 100,000 / 10,000,000 elements**, with **100 / 20 / 3 samples** respectively. Nonius, Criterium, PyTest.Benchmark and ScalaMeter handle timing differently; the article discusses calibration, outlier handling, JVM warmup and GC. C++ tracing collections are triggered before measurements, not disabled for the largest cases. The printed tables give rounded point values without interval columns; sample counts are not independent applications or development tasks.

Workloads sum elements by sequential indexing, iteration or internal reduction; append from empty; update each position in order; and concatenate ten equal-sized pieces. The [dated source](S211-rrb-artifact-check.md) further resolves retention and setup: update loops keep a starting persistent root but overwrite each intermediate result, while mutable-array copies are prepared before timing. The benchmark does not retain every update as an undo history. The retained source is not an exact cryptographic binding to the published runs.

The paper attributes a librrb update advantage to its simpler exception/memory-exhaustion handling, while the C++ implementation arranges potentially failing work before mutation. Its cross-language discussion acknowledges dynamic-language/boxing/runtime costs; table captions describe **sequential indexed access**, so the prose's broader random-access wording is not an independent random-access measurement. Clojure L cells are missing, not zero, and the reported slower monomorphic-vector trial and newer-processor RC overhead are explicitly informal. Preserve these limits without erasing the measured benefits.

Most importantly, **p.23 explicitly leaves the real-workload reference-count/move-reuse hypothesis untested**: the author did not find an unbiased benchmark of how dynamic aliasing changes the proposed advantage. The published table suite does not measure peak/retained memory, version-lifetime distributions, tail latency, complete interactive workloads, rollback effects, developer effort or subsequent change correctness. One-off implementation comparisons also cannot separately identify the effects of unboxing, visitors, allocation policy and language runtime.

## Consequence for Nu and the wider survey

For **B04/B06**, this supplies a concrete mechanism chain: persistent value API → shared tree and ownership checks → selective copying/mutation/free-list reuse → operation- and retention-dependent costs. Functional style is compatible with carefully encapsulated mutation. It does not imply that every update is free, that retaining history has no cost, or that persistent data structures were unique to Nu.

For **B01/B05/B10**, positions, policies and Python integration establish a realizable decomposition/interface alternative. The paper does not estimate lower comprehension or maintenance work. Its data-oriented-game application appears under future work. A funder-facing account can credit the scoped performance feasibility and identify Nu's actual integration/benefit question without promoting that future-work suggestion into an evaluated game architecture.

The next consequential alternative is **S213's acquired transient sequence**, including its ownership/complexity assumptions and explicit edition discrepancy; **S212's persistent iterators** can then settle access/mutation semantics and workload coverage. Earlier RRB foundations, retained-history measurements such as S145, and MapReplay/.NET representativeness remain available dependencies. Reading an additional method can close an understanding gap; it cannot itself measure an unobserved Nu benefit. No construction or experiment follows from this reconstruction.
