## Question, procedure and unit

The study asks whether an automated LLM pipeline can propose useful microservice boundaries, assessing reference similarity, design metrics and token consumption. It outputs a class-to-service JSON partition, not a refactored executable followed through later maintenance (pp. 3-7, sections III-IV, figures 1-4). Do not read the title as a behavioral maintenance experiment.

The pipeline ingests a pinned monolith, packs whole source files into 30k/50k/80k-token chunks, summarizes and either concatenates or LLM-merges the summaries; a seventh strategy uses AST segment/file/package/repository summarization. Only the resulting repository summary enters architectural-view generation. Five LLM views (components, component overview, endpoints, technologies and dynamic interactions) plus a source-derived dependency/call graph enter one-shot partition generation. Prompts contain no reference partition; there are no human corrections between phases (pp. 4-7). Supplying the static map is an information intervention, not passive measurement of unaided architectural understanding.

Four selected benchmark systems (JPetStore, Spring PetClinic, PartsUnlimitedMRP and 7ep-demo), four model families (GPT-5, Gemini 2.5 Pro, GLM-4.6, DeepSeek 3.2 Terminus) and seven strategies yield **112 decompositions, 28 per system**, with one run per cell (pp. 6-9). The systems, not those 112 outputs, are the independent application cases. Exact API snapshots, sampling parameters and invalid-output accounting are not fully specified in the PDF. The text calls summaries deterministic while describing LLM summarization/default inference; this does not establish stochastic repeatability (pp. 6, 11).

Reference service models come from paired implementations or published decompositions, constrained to overlapping functionality. SOTA measurements are reused from Wang et al.'s tool comparison after normalization/filtering, rather than rerun in the current LLM environment (p. 6). Reference and baseline provenance, normalization and prompts therefore need the replication package before exact reconstruction is complete.

## Outcomes and results

Table I (p. 5) defines MoJoFM reference similarity, cyclic independence, call-graph modularity, business-context purity, domain independence and contributor-cochange alignment, plus total input/output tokens. These are structural/socio-technical proxies. The existing reference is one valid architecture, not an oracle for all desirable designs; **no human architects assess the generated partitions**, and no runtime or downstream correctness measure is reported (p. 11, threats).

Table II (p. 8) reports LLM versus tool means: MoJoFM 27.33 versus 51.41; cyclic independence 87.83 versus 65.11; modularity 61.16 versus 62.93; team contribution 20.16 versus 31.19; domain independence 24.14 versus 34.84; business purity 44.21 versus 39.56. Derived differences are -24.08, +22.72, -1.77, -11.03, -10.70 and +4.65 metric points. The reported tests favor tools for reference/team/domain alignment and LLMs for cyclic independence; modularity and business purity are not significant. These nulls are not equivalence findings. Reported Cliff's deltas include -0.83 for MoJoFM and +0.44 for cyclic independence (p. 8).

The table's pooled comparisons do not supply a case-clustered uncertainty estimate; repeated strategies on four systems are not 112 independent systems. No new p-value or confidence interval is reconstructed without trial-level data. The apparent cross-system direction for domain independence is not universal: Spring's heatmap difference is +8.5 while the other three are negative (p. 10, figure 8).

Chunk-size tests are nonsignificant across 30k/50k/80k; e.g. MoJoFM means 27.35/27.37/27.27, p=.994 (p. 9). These are preprocessing chunk budgets, not an experimentally identified physical model context limit. The text reports total tokens of 226k (30k concat), 188k (80k concat), 184k (80k merge) and 736k (hierarchical), implying 3.26-4.00 times as many tokens for hierarchical relative to those examples (p. 10). Figure 7 uses log-scaled stacked bars; totals should come from the underlying data, not visual subtraction. Its caption calls the values averaged across four models while showing model-specific bars. A sentence in p. 9 repeats CiD 85.87 for hierarchical and AI comparisons; do not silently resolve the label ambiguity.

## Limits and ALF consequence

The authors identify one run per configuration, four Java benchmark cases, fixed prompts/views, class-level granularity, possible training exposure and API drift (p. 11). Their explanation in terms of shared architectural heuristics is an interpretation, not a measured internal mechanism. Neither the general Java characterization nor prototype/reference equivalence has been independently established here from pinned source.

**Correct the earlier abstract-only status:** the complete author preprint is now read. **Narrow the overlap claim:** partition generation, architectural maps and structural evaluation are occupied prior methods, but this paper's evaluated outcome does not establish future behavioral maintenance. ALF should retain public obligation-based runtime scoring, compare against credible alternative implementations, and keep a structural proxy separate from behavioral correctness. Treat any supplied architectural map or extra summarization stage as a policy change with its cost recorded. The paper supplies no empirical validation of Nu, no human-expert endorsement of ALF, and no permission to infer that larger contexts cannot help.
