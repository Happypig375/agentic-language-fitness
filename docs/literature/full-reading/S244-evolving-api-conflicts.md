# S244 — evolving APIs, documentation and update adoption

Ahmed Nusayer Ashik, Shaowei Wang, Tse-Hsun Chen, Muhammad Asaduzzaman and Yuan Tian, *When LLMs Lag Behind: Knowledge Conflicts from Evolving APIs in Code Generation*, [arXiv2604.09515v1](https://arxiv.org/abs/2604.09515v1), 10 April 2026, [DOI10.48550/arxiv.2604.09515](https://doi.org/10.48550/arxiv.2604.09515). Main-agent reading, 2026-10-04.

The paper reports substantial gains from supplying API documentation, with further aggregate gains from reasoning/self-review instructions. It distinguishes using the requested new API from producing code that runs. These are useful results for changed external requirements. The study generates demonstration programs rather than maintaining an existing application; its execution endpoint is conditional on judged adoption, and released tables have unresolved denominator discrepancies. Neither successful process exit nor use of a requested API establishes correct new and retained behavior.

## What changes, and what the model must do

Sections 3–4 select **270 Python API updates** after December 2023, divided into deprecations **P1=45**, modifications **P2=128** and additions **P3=97**. Table 1 names NumPy, Pandas, SciPy, scikit-learn, Matplotlib, Keras, JAX and PyTorch. The prose instead includes TensorFlow where the table/artifact use Matplotlib; the actual table/data identities govern this reconstruction. SciPy contributes 118 cases and PyTorch only one, so equal treatment of libraries is not implicit in the corpus.

GPT-5 Mini extracts changes and structured documentation from release notes. Two authors reportedly review all cases, resolve disagreements and discard incomplete, misclassified or undocumented updates. Deprecations need a documented replacement. This favors documentable demonstrations; the initial extraction yield and all exclusion decisions are unavailable. The post-December-2023 selection rule and the paper's model-cutoff table are assumptions about exposure, not direct measurements that a model previously knew the old API and lacked the new one. The study does not isolate parametric-memory conflict from unfamiliar APIs or difficulty following context.

Each prompt requests a self-contained runnable demonstration using the changed/new function or replacement. The treatments are **update description (UD)**, **UD plus documentation (Doc)**, **Doc plus chain-of-thought instruction (CoT)** and **Doc plus CoT plus self-reflection (CoT+SR)**. Documentation can include signatures, parameters, return values, notes and example programs. This is useful permitted task information; its quantity and content are not matched to the short UD condition. No SR-only arm is shown.

The released generation notebooks implement CoT+SR as extra instructions in **one model call per case**. CoT asks for internal reasoning while forbidding reasoning in the final answer; SR asks the model to check/improve its answer before returning code. There is no separate programmatic review/regeneration loop or executed-test feedback in these wrappers. The paper's conceptual review stages should not be counted as observed additional model calls.

The eleven model configurations are DeepSeek-Coder 1.3B/6.7B/33B, CodeLlama 7B/13B/34B, DeepSeek-R1-Distill-Qwen 1.5B/7B/14B/32B and GPT-4o Mini. The paper describes Python 3.10, four RTX3090s, 256GB RAM and 8-bit loading for large local models. Released local/GPT output caps vary by pattern: **P1 2,048/512**, **P2 512/512**, **P3 512/1,024**. Local generation is greedy and the GPT wrapper specifies temperature zero. Mutable model variables and reused output-folder labels are not a complete campaign manifest. No exact repeated-trial, service-version, token, latency or total-cost ledger is released here.

## Endpoints and reported outcomes

| Endpoint | Definition and consequence |
| --- | --- |
| Adoption Rate | GPT-5 Mini judges whether the output uses the requested updated API at least partially appropriately, divided by all outputs. Incorrect parameters can still qualify. The paper reports **91.4% accuracy against 1,000 author-annotated samples**; no complete labels, confusion matrix or stratified agreement packet is available. |
| Executable Rate | Error-free programs divided by **judge-accepted adopting programs**, according to the stated formula. Different treatments select different subsets. This is neither an all-assignment success rate nor an independent semantic test. The released runner treats zero exit status as success and supplies no expected-output assertions. |
| Error categories | GPT-5 Mini classifies remaining nonadoption/execution errors; author checking of 20 nonadoption and 30 execution failures gives **45/50 agreement**. These are selected failure descriptions, not causal estimates of stored-knowledge interference. |

The paper reports mean adoption **74.64% → 92.87%** and conditional execution **42.55% → 66.36%** when documentation is added. The latter is about **23.81 percentage points /55.96% relative** improvement. Preserve this favorable aggregate result. Adverse cells remain material: CodeLlama13B's P2 execution goes **41.90% UD →14.29% Doc →30.77% CoT →64.17% CoT+SR**. GPT-4o Mini's P2 result is **77.69% UD →70.16% Doc →76.80% CoT+SR**. DeepSeek1.3B's P1 falls from **77.27% Doc to66.67% CoT+SR**. GPT-4o Mini has favorable overall Doc outcomes, while size trends are nonmonotonic in many family/pattern groups. Aggregates, model size and the presence of reasoning instructions therefore do not guarantee improvement for an individual change.

The strongest condition leaves a reported **195 nonadoptions**: 82 omit the target, 32 use the old API, 24 mix old and new, 31 hallucinate an API and 26 have other errors. The paper separately reports **781 adopting but nonexecutable outputs**, with 52.1% classified as update-related and 47.9% unrelated. Update-related failures include wrong parameters, invented behavior and incompatible surrounding context. These are useful accounts of distinct failure modes, with classification and denominator limitations below. Mixed old/new usage being classified as nonadoption also requires a more exact rule than the coarse “at least partial” description.

The `np.unique` versus requested `np.unique_values` example illustrates an **explicit API-adoption requirement**: an old API can compute the intended values yet miss the requested implementation constraint. That is a legitimate endpoint for this task. It must not be transferred into a generic rule that functionally correct alternative edits or D1 catch-alls fail. Application behavior, source constraints and executable status remain separate obligations.

## What the released artifact corroborates and leaves unresolved

The JSON files contain **89 raw deprecations, 128 modifications and 97 additions**, plus 45 replacement-documentation records. The P1 generator's exact replacement-name lookup retains **45 of89**: JAX4, NumPy17, Pandas3, PyTorch1, SciPy19 and scikit-learn1. These match Table1, as do all P2/P3 library counts, recovering the selected **270** cases. The larger raw deprecation count is therefore not an unresolved sample-size contradiction. Five replacement names each have two different documentation records; the generator chooses the first exact match, so their order affects the supplied content.

The twelve Keras3.10.0 rows are placed in P2, but **eleven are labeled `added` and one `signature_changed`** in the released data. All twelve lack parameter/return/function-description fields and have empty code-example/note fields. The P2/P3 Doc prompts serialize remaining JSON fields after removing identifiers/description fields; they do not fetch complete official documentation at inference time. Keras therefore has a materially thinner Doc treatment, and its P2 grouping does not consistently mean modification of an existing API. This is a released-label/content discrepancy, without an independent historical adjudication of all APIs.
