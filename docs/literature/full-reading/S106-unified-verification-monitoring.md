## Positive mechanism and observation contract

The useful contribution is a **shared executable property representation**. The Embedded Model Interpreter (EMI) runs both a system UML model and a property UML state machine (PUSM). A generic semantic transition relation exposes configurations, enabled actions and successors; a synchronous product combines the two interpreters. Property predicates inspect the system through an observation language. Reusing the same deterministic observer offline and on a device avoids a separate generated monitor and its model-binding step (Sections 4–7).

This is a restricted executable UML interpretation: classes, composite structures and flat state machines, with C guards/effects. A configuration contains the interpreter's dynamic memory; actions represent run-to-completion steps. Selecting among enabled actions may be nondeterministic, while executing a selected EMI action yields one successor. Generic STR definitions allow sets of successors. C guard purity and effect termination/atomicity remain designer obligations; the interface does not enforce them. Hierarchical states and compound transitions are proposed extensions. An optional LTL-to-Büchi-to-UML path exists, so “transformation-free” describes the central shared-interpreter route, not the absence of every translation in the toolchain.

| Use | What is searched or observed | Conditions and limits |
| --- | --- | --- |
| Offline Büchi checking | Product of the closed system/environment model and an automaton recognizing property violations; accepting-cycle search | Abstract scheduler/environment and the encoded atoms define coverage. Deadlocked subject states receive stuttering transitions so the property can continue. Pruning an unmatched property transition relies on a correct automaton encoding. |
| Offline observer checking | Reachability of a failure state | Multiple observers can follow the same system. A missing enabled observer edge gets an implicit self-loop, preventing the observer from blocking system progress. This completion is distinct from subject-deadlock stuttering. |
| Runtime monitoring | One actual scheduled system step followed by the corresponding deterministic observer step | The scheduler chooses first; the system action fires once before the observer advances. Deterministic, complete observers are reusable; arbitrary nondeterministic Büchi checking is not thereby performed on the device. |

Offline exploration closes the system with an **abstract environment and scheduling policy**. Runtime execution instead uses actual scheduling and physical or simulated I/O. Shared observer semantics remove one translation boundary, but cannot establish that the abstract environment covers every relevant deployment behavior. The paper explicitly retains monitoring because abstraction can miss behavior, state spaces may be too large, or hardware may fail (Section 7.2). Successful monitoring covers the observed execution; it does not establish an exhaustive liveness result.

The cruise-control interface (CCI) example separates controller, pedal manager, actuation and cruise-speed manager from an abstract vehicle/control loop. The abstract engine permits unrelated successive speed values, including a 0-to-100 km/h jump, to overapproximate physical possibilities (Appendix A.1). Speed is bounded to 0–200 for tractability (Section 9.5). This is a stated abstraction strategy, not a verified simulation relation to every vehicle or game environment.

**The actual atoms matter.** Appendix C defines stop/set/resume predicates by presence in specified event pools; on/off/setpoint predicates instead inspect the oldest event in a peer's pool. These are not generic “event happened” or “event consumed” predicates. R3 uses strong until: once its antecedent holds, the throttle-release event remains pending until a resume event appears. R4 uses weak until for forbidding setpoint updates before on. Unknown cruise speed is the explicit value `-1`. Queued inputs, object-state predicates, transition identity and output consumption therefore need their own correspondence when transferring this method to Nu. The nineteen diagrams and language operators expose these choices rather than leaving observation implicit.

## Reported outcomes and costs

The authors report applications in five domains, but the detailed results here concern the CCI and six selected requirements (Section 8). This is useful demonstration and measured-cost evidence, not five independent comparative benefit studies.

- **Defect discovery and repair:** three liveness requirements pass the separate/combined Büchi checks. Of three safety requirements, the sixth fails: the system can be engaged while cruise speed is undefined. Counterexample analysis identifies and fixes a bad event interleaving. The corrected model has **17,134,122 configurations and 29,088,210 transitions**. Preserve this successful finding and repair.
- **Alternative property encoding:** the same requirements expressed in LTL yield the same OBP2 verdicts. PUSM checking averages **6.7% less memory and 7.4% less time** for this example. Both routes share atomic propositions and system semantics, so agreement is an encoding comparison, not an independent validation of intended requirements. The authors suggest the C composition implementation versus the LTL route's Java implementation as an explanation; it is not an isolated effect of graphical versus textual specification.
- **Runtime observation:** deployed model-checked versions show no detected failures. STM32 Discovery boards use actual sensors/actuators where available and a simulated environment otherwise; the latter matches the verification abstraction. For the initial buggy CCI, the text says the observer would detect the failure **if it occurred**. This is weaker than a reported observed runtime fault detection and supplies no general sensitivity estimate.
- **Runtime cost:** CCI execution-time overhead is **50.8% measured**, versus **50.2% estimated**; synchronous composition alone contributes about **6.5%**. Measurements compare **1,000,000 transitions** with and without observers. Reported **8.2% memory footprint overhead** comprises about 1.2% composition plus 7% for three observers, but the measurement is **binary executable size**, not resident memory or peak heap. No frame/deadline tails, trial variability or developer-time comparison is supplied.

The timing approximation is `6.5 + (100 / number_of_active_objects) × sum(outgoing_edges / observer_states)`, excluding initial pseudostates and failure states from the state denominator. Its relative-cost intuition depends on the work per object and guards; it is not a universal scaling law. Most importantly for games, the stated scope is **single-core systems without real-time constraints** (Section 9.5). These costs neither establish nor rule out acceptable Nu frame latency.

Section 8.3 extends passive observers into fail-safe controllers by adding an action that sends a stop event on entry to failure. Its checked temporal formula says, after observer failure, subsequent stop events must eventually lead to disengagement. **Our logical reading:** that conditional formula does not itself require a stop event to occur; the event-producing action is a separate part of the implementation. Nor does the formula prove real sensor/actuator reliability. This is a constructive enforcement example with explicit premises, not a universal recovery guarantee.

The source declares STR, implicit transitions and synchronous composition. It does **not** contain the EMI adapter promised by the README, a complete C implementation, the CCI result packet or a proved implementation-correspondence theorem. The README's embedded Lean-editor URL is another representation of these definitions; it was read as text and not executed.

There is a material static limit to treating the definitions as a correctness certificate. `add_implicit_transitions` line 31 uses a universal equality over all enabled actions, and the product's initial set at line 46 likewise requires equality to every initial pair. With two distinct enabled actions, no wrapped action can equal both; with two distinct initial pairs, the latter set is empty rather than a Cartesian product. Conversely, an empty quantified domain can make the constraint vacuous. This is elementary interpretation of the displayed definitions, **not a Lean/compiler run or an observed fault in the C interpreter**. The journal's generic set notation and the public literal definitions do not establish correctness of the reported implementation. It repeats a formalization pattern located in S105; these are related sources, not independent adverse experiments.

The result remains worth using at its actual scope: a shared property/interpreter design, an identified model defect and concrete time/size comparisons. The full runtime implementation, raw repeated measurements and publication-run correspondence are not recovered by this two-file release. Further artifact work is conditional on a claim requiring them, not an automatic task to reconstruct an unavailable toolchain.

## Consequence for Nu and the next consequential gap

For **B03/B04/B06/B07/B08/B10/B12**, reusable state and common semantics enable useful inspection, but the observation contract still needs an environment, scheduler, event meaning, pending monitor state and cost unit. The funder-relevant question is whether this integration yields more correct completed changes or useful diagnosis per total development/runtime cost in the intended workload. Generic “verification plus live state” is already prior capability; neither a shared interpreter nor successful finite monitoring establishes that empirical benefit.

Use S105/S106 together: branch-specific future witnesses need explicit initialization/history semantics, while deployment monitoring follows the actual trace and has measurable overhead. These methods refine potential Nu comparisons without dictating adoption of UML or authorizing D1 construction.
