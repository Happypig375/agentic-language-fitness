## Contribution and evidence class

The paper provides a conceptual framework and eight challenges across six cases. It explicitly presents no new solution. The cases connect live Elm-style applications, relational data, computational documents, enduring version divergence, changes in field multiplicity, and executable modeling languages. These are reasoned examples, partly drawn from the authors' research, rather than six independent empirical studies or a sampled distribution of real maintenance changes. The paper does not supply a controlled usability, correctness, productivity or runtime comparison.

Schema is deliberately broad: an explicit database definition or type, or an implicit expectation about a document/data structure. It constrains two other layers, data and code. Data includes persistent records and live runtime state; some computed transient data may be discarded and recalculated. Changes can be local or propagate across program variants. Variants may converge on all changes or retain selected differences indefinitely, and changes may originate centrally or independently. These dimensions help separate questions often collapsed into “state preservation.” They are not a proof that every combination has been covered.

The paper's desired outcome is coordinated change of schema, data and code, with minimal disruption to the person using the system. “Minimal harm” is an aspiration here, without a general distance metric, behavioral oracle or measured optimum. A structurally nearby, well-typed result can still violate intended behavior.

## Eight challenges and their consequential boundaries

| Challenge and pages | Concrete obligation | Limit relevant to Nu/ISE |
| --- | --- | --- |
| 1. Live state type evolution, pp. 5–7 | Change an Elm-style `State`, its current value, and affected update/render code together | Changing a completed flag into an optional timestamp requires a meaningful mapping/default. An exhaustive new event case does not supply that meaning. The claim that changing `Event` needs no data migration assumes no unprocessed events. |
| 2. Extract Entity, pp. 7–9 | Separate repeated customer attributes into identities and references, deduplicate values and retain relationships | Equal attributes need not mean the same entity; typos may hide duplication. Merging can lose information needed to split again. The inverse is an open semantic choice, not guaranteed by a schema change alone. |
| 3. Code co-evolution for Extract Entity, pp. 9–10 | Rewrite dependent queries to use the new linked tables, or preserve compatibility through a view | Data migration does not by itself preserve query behavior. The proposed equivalence involves schema, data and queries together. Replicated deployment must also handle operations already in flight. |
| 4. Structured document edits, pp. 10–12 | Merge a new/sorted speaker list with a concurrent list-to-table transformation | New rows need values for newly introduced columns. The desired order-independent merge is qualified by the available edit operations and possible user conflict resolution. |
| 5. Code co-evolution for document edits, pp. 12–13 | Retarget formulas/selectors when the document's structure changes and invalidate or recompute affected values | Convergence of document content does not establish that formulas still refer to the intended data. Permanent and transient data have different preservation duties. |
| 6. Divergence control, pp. 13–16 | Transfer data changes between users who deliberately retain different schemas and code | A one-time migration or eventual adoption of every change is insufficient. Bidirectional transfer and selective merging require explicit correspondence and conflict policies. |
| 7. Multiplicity change, pp. 16–18 | Keep scalar and list views interoperable while users continue editing either view | A scalar edit cannot reveal whether the user intended to remove, replace or preserve hidden list members. The application must choose or ask for a policy. |
| 8. Live editing of DSLs, pp. 18–22 | Patch a running state-machine instance after changes to its defining model | Deleting the current state, changing transitions with pending events, and changing variable types need policies beyond structural patching. Editing the metamodel can additionally require changing the program instances and interpreter. |

The multiplicity example gives a compact counterexample to automatic inference of intent. The old view shows assignee A; the new view contains `[A, B]`. Writing C through the old view is consistent with `[C]`, `[C, B]` or `[C, A, B]`, under different intentions. All can keep the displayed scalar equal to the first list member. That representation invariant cannot select the intended preservation/deletion policy.

For live DSLs, the paper distinguishes edits considered structurally simple from their runtime consequences. Adding or renaming a state can be patched at a suitable interpreter point. Removing the current state may require rejecting the change or selecting another state. Removing a transition or changing its event may leave queued events stale. Renaming a variable should retain its value; a type change may convert or reset it. These are specified possibilities, not an implemented comparison establishing which policy is best. Quiescence alone does not supply the missing domain policy.

Higher-level edit histories can expose a rename or refactoring that is ambiguous in a textual before/after diff. They also require a representation/editor and a supported operation set. Their usefulness cannot be treated as free information available to every tool or coding agent. A method that knows the intended transformation differs from one asked to infer it from arbitrary source edits.

## A consequential citation correction

Section 9, p. 24, groups hot reloading/swapping references [6,33] under a description that preserves some state without attempting to migrate it through type changes. Reference [6] is the already fully read [S71](S71-live-state-migration.md). Reopening S71's PDF pp. 2–3 confirms that its explicit objective and mechanism include migration between different state types, with defaults, structural correspondence and optional custom conversions. Its section 7 separately warns that the resulting type does not guarantee application invariants.

The broad p. 24 characterization therefore cannot be carried forward as an accurate account of S71. A defensible distinction is between S71's actual, restricted type-directed migration and S73's wider demands for semantic intent, code/data co-evolution, collaboration and lasting divergence. This correction does not show that S71 solves all eight challenges, nor that Nu does. S73's narrower discussion of systems that restart after particular edits should also remain tied to the actual systems and versions, rather than generalized from this sentence.

The adjacent summaries of database tools, language workbenches, bidirectional transformations and code migration are useful discovery guides. Their historical or universal limitations require checking the cited primary methods and current editions before using them as absence claims. Reading S73 is not equivalent to reading its bibliography.

## Three criteria and implications

**Unique:** treating interactive evolution as coordinated changes to state shape, data and code has direct prior framing, with earlier migration and transformation mechanisms. Broad firstness for this problem fails. Any claimed Nu distinction must identify its actual operation, representation, effect boundary and supported changes. Priority of the narrowed F#/agent contrast remains unconfirmed.

**Valuable:** the examples identify concrete losses, stale events, broken formulas and incompatible clients that matter to a maintainer. They do not estimate task prevalence, avoided effort, adoption cost or net benefit. A claimed improvement must say which of these obligations it addresses and what a user must still specify.

**Scientifically valid:** use the challenges as analytical distinctions, not as a validated benchmark or an automatic expansion of D1. A future study would have to declare retained/dropped state, pending work, identities, defaults, compatibility and user-intent policies before judging correctness. Existing D1 boundaries and experimental holds remain unchanged. Exhaustiveness, well-typedness, replica convergence and complete behavioral success are separate endpoints.
