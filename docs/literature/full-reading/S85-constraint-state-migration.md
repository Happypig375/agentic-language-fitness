## Live claim and prior mechanism

B02/B03/B04/B06/B07/B08 ask what makes retained state valid after a program edit, how pending work changes, and what live migration costs. S71 preserves required types with restricted correspondence and conversions; S73 distinguishes that from domain intent. S85 adds an earlier **explicit invariant-and-policy mechanism**: given an old program `p`, old runtime state `x` and new program `p′`, find a new state `x′` satisfying language-designer constraints. It does not infer the intended migration policy from an arbitrary edit.

Nextep distinguishes semantic relations `R(p′, x′)` from migration rules `M(p, x, p′, x′)`. The first constrain a runtime state relative to the new model; the second encode how old and new versions should correspond. Several results may satisfy both. A generic distance heuristic favors fewer changed relation tuples and smaller absolute integer changes. “Nearest” in this representation does not prove the result is least harmful to the application or least surprising to its user; the paper explicitly leaves other heuristics and empirical usability open.

The finite-state-machine example records a current state and visit counts. Adding a state preserves the current state and old counts, initializing the new count to zero. Removing the current state resets it to the initial state **because the designer writes that rule**. Choosing the closest surviving state would be a different valid policy. Without the rule, a surviving state can be selected arbitrarily. A type-correct or constraint-consistent state therefore remains distinct from the desired state.

Nextep describes static and runtime classes separately, so the runtime representation need not be a subclass-based extension of the static metamodel. It translates specifications into AlleAlle's bounded relational model, then into Z3 SMT constraints. Object/relation search is bounded by existing atoms plus finitely many auxiliaries, even though integer arithmetic is unbounded. Static validity is assumed to be enforced elsewhere in the simplified printed example. The construction presupposes a step-based interpreter that can pause around an edit and a designer-defined account of what belongs to runtime state.

The migration uses the immediately preceding state, not the full execution trace. A policy selecting a previously visited execution state cannot be expressed merely by consulting an absent history. The paper does not establish arbitrary call-stack, native resource, network or physical-effect restoration. It also leaves seamless delivery of the inferred state back to the user/interpreter as future work. These are scope boundaries, not missing pieces silently supplied by “live.”

## Pending work and the robotic example

The second DSL coordinates a robot's subsystems through a request pool, per-subsystem queues and inter-action dependencies. Adding a trigger action introduces a new dependency for an already queued arm action. An explicit rule places newly added actions in the request pool; semantic constraints then move the affected arm action back out of its queue. Table 5 illustrates that a structural edit can require changing **pending work**, rather than only adding a default-valued field.

This is one qualitative author example demonstrating expressiveness. It supplies no physical-robot trial, independent safety oracle, user comparison or task distribution. The constraint set, correspondence, distance objective and interpreter/effect boundary still require validation. Inferring a consistent abstract queue is not evidence that completed physical actions can be undone or that every future behavior is correct.

The comparison to RMPatch is conceptual. The authors identify coupling of static/runtime models, ordering of imperative patch operations, transient inconsistency, scattered invariants and invasive extensions. Nextep can express additional constraints conjunctively and delegate interactions to a solver. No controlled authoring-effort, defect, extension-cost or latency comparison with RMPatch is supplied. Conjunction may introduce conflicts or unsatisfiable requirements; modular syntax does not demonstrate independent or compatible policy extensions.

## Performance evidence and denominators

The quantitative evaluation uses the same synthetic state-machine family and two changes: adding one state/two transitions and deleting the current state. The paper reports ten runs per size on a 2015 MacBook Pro, measuring Nextep-to-AlleAlle translation, AlleAlle-to-SMT translation and solving. No human maintenance outcome is measured. Figure 2 shows that translation can dominate the total; a solver-only time is not complete live-update latency, and interpreter resumption/user display costs are not established by these phases.

The paper reports **9/19 and 13/19 configurations timing out**, respectively, with an empirically chosen **three-second solver limit** after observing a divide between short solutions and multi-minute searches. Timeout is failure to obtain the requested optimal solution within that limit, not a successful three-second migration, proof of unsatisfiability or a bound on unrestricted solve time. The figure shows configurations from six through 25 states, and the released data for that displayed interval contain twenty sizes; preserve the printed nineteen-denominator discrepancy rather than silently changing its percentages.

The paper describes prototype optimization opportunities, including manually simplified encodings and a proposed native-Java translation speedup. These are not an end-to-end evaluated replacement. Its conclusion's “satisfactory” performance assessment is qualified by the reported timeouts, unpredictability and unfinished integration. No Nu, general DSL, contemporary-solver or real-time-game performance rule follows from this prototype.

## Bounded released-source and aggregate check

The cited GitHub directory initially returned a web cache error; direct GitHub API access succeeded. The inspected snapshot is [commit `b3024f49818eefc0fab18bb6dddaadb96c331453`](https://github.com/cwi-swat/live-modeling/tree/b3024f49818eefc0fab18bb6dddaadb96c331453), dated 2 November 2018, the last commit returned before the conference end date. This is a dated available artifact, **not a verified experiment-build identity**. Fourteen selected files were downloaded and hashed: README, robotic Nextep/manual AlleAlle specifications, pipeline, four benchmark-source files, and three aggregate/raw result pairs. The rest of the repository, dependencies and VM remain unexamined.

The following checks reconstruct stored data and inspect source; they do not reproduce execution:

- `result_scenario1` and `result_scenario2` each contain **35 sizes, 6–40, with ten observations each**. The six-to-25 subsets reproduce the figure's timeout-size lists exactly: nine and thirteen sizes have all ten stored solve times at least 3,000 ms. The wider released sets have eighteen and nineteen such sizes. This is 700 stored benchmark observations across two generated families, not independent applications or human tasks. `scenario1b` adds sixty observations over sizes 10–15 with different values and timeout patterns; it is kept separate.
- All stored individual total times equal their three component times. However, the aggregation function named `getMean` sorts observations and, for ten values, averages the **sixth and seventh** values with integer truncation. This is neither the arithmetic mean nor the conventional median. All **304** checked labelled-mean cells across the three result sets match that function. For scenario 1 with six states, the first translation's labelled value is 1,247 ms, versus arithmetic mean 1,250.6 and median 1,239. The original figure-generation source/build is unverified, so this finding qualifies the released aggregate labels without claiming an independently reconstructed publication plot.
- The source warms up the process and clears selected memo caches between measured calls; it does not visibly launch a fresh process for every run. The paper's broad independence/no-shared-cache description is therefore not established by this selected runner. The Nextep phase uses `userTime()`; cross-phase clock equivalence and complete wall-clock latency were not verified.
- The stored aggregate range, paper's stated 943–1,529 ms translation range, benchmark entry-point ranges and `scenario1b` outputs are not identical descriptions of one verified run. Do not choose whichever set looks most favorable or pool them as one experiment.

The [robotic specification](https://github.com/cwi-swat/live-modeling/blob/b3024f49818eefc0fab18bb6dddaadb96c331453/nextstep/input/roboticarm.nxst) also differs from printed Listing 3. The publication uses `request.actions` although `request` is declared as a set of `Action` and the displayed `Action` class has no such field; its nonintersection expression compares the queued wrapper objects without projecting their `item`. The available source uses `q.actions.item` and `request`, and a different old/new selection syntax. These visible differences prevent treating the printed listing as a verified executable oracle.

A further unresolved ordering detail appears in the source: the old example gives predecessor `down` index 1 and successor `up` index 2, while its same-queue constraint requires the predecessor index to be greater. The separate manual AlleAlle file uses another encoding/order convention. The method constrains a newly inferred model, so this inspection alone is not an executed failure or proof that every resulting migration is wrong. It identifies a correspondence/queue-semantics check that must precede reuse. No source was patched to manufacture agreement.

## Implications and consequential follow-up

**Unique:** constraint-directed migration with explicit semantic and transition policies, separate static/runtime representations and a least-change objective predates the present Nu investigation. The general capability is not a new contribution. Any Nu distinction must name the supported edits, policies, state/effect boundary and operational integration. **Valuable:** the examples address concrete state-loss and queued-work problems, but no maintainer-effort, adoption or net-benefit estimate is supplied. **Scientifically valid:** validate the constraints and migration intent independently; distinguish solution existence, optimality, timeout, state consistency, successful resumption and retained future behavior. None of this validates D1 or authorizes new experiments.

SC25/SC26 verify RMPatch, Echo and Kodkod performance identities and leave the UML/OCL cost-policy source unindexed; the latter's ten-page CEUR file is reachable but its body remains unread. Backward transformation, policy-choice and scalability methods remain open. The eight-edge incoming graph is not field completeness. S73 is an already-read framing paper; Bacatá and sustainability modeling are contextual, and a proceedings-level DOI is not an independent experiment.

SC27/W22 identify **S99**, the later Live-UMLRT generated-code study, and **S100**, integration of model checking into a live modeling environment, as primary follow-ups. Their claims concern safe updates, replay, latency/resource costs, and witness traces integrated with current execution/edit history; methods and artifacts remain pending. Sullivan's 2023 *Live Programming for Finite Model Finders* has author-abstract/first-page discovery coverage: it proposes closer interaction with solutions, not an established fix for Nextep's runtime-scaling problem. Preserve this distinction rather than inferring progress from the title.
