## What the environment actually provides

This Squeak/Smalltalk prototype combines ECS, hot code replacement and tools aware of the running game. Entities have identities, components hold data, and systems query/update components. The editor offers component definitions, editable queries, system code, game views, time/snapshot controls and profiling. Screen arrangement reflects system execution order, which users can change. Query connections and moving bubbles show component usage and query-result size; these are not a correctness proof or complete causal graph.

Snapshots are deep copies of component state. The paper separates initial state Δ0, current state Δi and replay starting state Δr. Changing only Δi is temporary. Persisted changes may update Δ0, Δi and Δr; recorded external inputs can be replayed from Δr. A restart returns to Δ0. Automatic restart after edits attempts to recompute effects from Δr, or Δ0 if no replay snapshot exists. Replay after edits is thus different from simply inspecting an unchanged trace.

The distinction matters for derived state. If initial health 200 has fallen by 150, overwriting both initial/current health with 300 loses the prior damage. The supplement's Figure 3 illustrates restarting before the damage to derive 150 under the new initial value. The example assumes a suitable preceding snapshot and reproduced inputs; it does not prove arbitrary edit migration or consistency for effects occurring before that snapshot.

Runtime-created entities may have no counterpart in Δ0. The UI colors fields that cannot be persisted. Templates and an `InstanceOfTemplate` marker support updates to spawned instances, but overwriting their values still risks discarding derived history. Explicit persistence mode and visible warnings expose the choice; they do not infer a universally correct historical state. A future Nu comparison must distinguish temporary experimentation, source/template edits, initial-state changes and migrated live state.

Inline watches display values without pausing; editable query fields freeze the entry field while separately displaying the changing live value. The supplement describes error recovery through Smalltalk's debugger or retry after a save. Game-specific tool systems can draw overlays, manipulate objects or provide multiple views. Reusing them across games was difficult when component layouts or camera projections differed; higher-order parameters were explored. Tool/game co-location is a design hypothesis about cognitive effort, not a measured reduction.

## Evidence and adverse cases

The evaluation consists of the authors building three small prototypes: an isometric random map/culling renderer, tower defense with pathfinding/balancing, and a platformer with simple physics/level placement. Examples include path overlays, replaying a jump to place tiles, template tuning and camera views for culling. These establish implemented possibilities and author experience. They are neither independent user assignments nor a controlled comparison with traditional engines.

The papers report no quantitative task-time, repair-success, iteration-count, game-quality or maintenance-effort comparison. The supplement explicitly leaves quantitative analysis and scaling to larger games/changes for future work. Its use of “benchmark” for exploring drawing/rendering does not supply a numerical benchmark result. Larger refactorings and edit transactions are future directions. Contemporary Godot/Unreal capability claims cannot be inferred from this 2021 comparison; this review does not use those historical descriptions as current product facts.

The supplement adds a consequential visibility/cost tradeoff. The entity-filter UI updates after a tick. A collision entity created by physics and removed by cleanup in the same tick therefore never appears in that inspector. Multiple intermediate changes are likewise omitted. Recording more detailed mutation history would impose additional work. The description of taking end-of-tick state without history overhead must not become a claim that snapshots, copying, rendering, watches or the entire tool are free. Software rendering was costly in the map example; an OpenGL variant was explored without published quantitative results here.

## Bounded dated-source comparison

The paper-linked [repository](https://github.com/hpi-swa-lab/tools-interactive-simulations) was inspected at `abb0354f10974d872016c191fd7817271165b965`, dated 2021-10-12. Its recursive tree has 5,204 entries and is untruncated. The complete README, nine `ECSSnapshotReplay` instance-method files, five selected `Universe` methods and `TimeSystem>>tick:` were read. This is sixteen files, not the whole implementation or a verified paper-build artifact.

The README requires tool-compatible components, including `DeltaTime`, `UniverseView`, `Transform` and `KeyEvent`, and describes systems as accessing component state. The replay code copies universe state, records `externalEvent` values with elapsed time, dispatches specific mouse/key/editor event kinds and resets from the copied state. This supports a concrete event/snapshot mechanism rather than arbitrary VM or external-world rollback.

Two source qualifications matter for independent verification. `TimeSystem>>tick:` uses the current millisecond clock; `playSnapshot` resets its last-clock value. The selected methods do not demonstrate replaying a captured sequence of every original timestep. Thus the exact-input-and-sample-time conditions in S46/S47 must not be silently imported into this prototype. Separately, `Universe>>set:in:of:to:persist:` emits a mutation event carrying the persistence Boolean before conditionally updating initial state. Its replay listener `snapshotSet:in:of:to:persist:` updates an existing replay snapshot without testing that Boolean. That source path differs from the prose rule that nonpersisted edits affect only current state. These are versioned source observations requiring validation, not reproduced failures, proof that every editing path behaves this way, or a claim about another release.

The loop's timestamp-interval boundaries, zero-duration recordings, nondeterministic inputs, edits involving missing entities and runtime effects are additional candidate verification cases. No test was executed to adjudicate them. Exact experiment-build equivalence, generic deterministic replay and complete external-effect capture remain unestablished.

## Three criteria and consequential follow-up

**Unique:** live game editing, component snapshots, input replay and integrated overlays have direct Smalltalk/ECS prior art. They cannot be claimed as newly enabled only by functional purity or Nu. **Valuable:** the tasks and visibility problems are concrete; author experience does not establish net productivity, game quality or agent-maintenance benefit. **Scientifically valid:** control tool access, replay inputs/timesteps, temporary versus persisted edits, history visibility and transient events; measure complete behavior and total cost independently.

The twenty-edge incoming Scite request returned two edges/three nodes, untruncated but flagged low coverage. A twenty-record DOI check identifies a live-development literature review and block-based scaffolding study. These remain conditional on broader taxonomy/educational claims. Four backward identities were checked with twenty requested records: *It's alive!* (`10.1145/2491956.2462170`), edit transactions (`10.22152/programming-journal.org/2017/1/13`), game-tool expectations (`10.1145/2460999.2461004`) and the 2019 game-liveness position paper (`10.1109/CIG.2019.8848092`). They remain conditional on adopting their specific mechanisms, transaction guarantees or prevalence claims; their methods are not silently credited.

The exact Pronto 2023 title returned zero in Scite. Its official PPIG abstract describes a Godot framework and a student course that extends it. The primary follow-up [All in One: Rapid Game Prototyping in a Single View](https://doi.org/10.1145/3706598.3714251), CHI 2025, was identified and its abstract and selected opening passages read: it directly compares Pronto with Godot through a walkthrough and exploratory user study. **Promote its full methods** because access-speed, structure, documentation and usability tradeoffs can change the live-game benefit claim. The 2023 precursor remains conditional on details not covered by that later study. The 2025 omniscient-debugger study promoted from S63 also remains active. No fixed reading ceiling or experiment authorization follows.
