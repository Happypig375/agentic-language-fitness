## Mechanism and interface obligations

LibFpp's contribution is an **iterator carrying its own logical container version**. Updating a cursor changes that cursor's version; the originating container and other cursors retain theirs. The caller must explicitly extract the changed container with the paper's `it.value()` operation, called `finalize()` in the released source. This avoids invalidating other iterators through container replacement. It does not make assignments to a shared cursor variable race-free, deeply freeze arbitrary referenced payloads, or roll back external effects. A value API can coexist with variable reassignment and selectively mutable physical storage.

Containers share a measured finger-tree representation. End digits and recursive2–3trees support amortized constant-time end operations, logarithmic interior access and efficient join/split. Sequence length, ordered-container summaries and UTF-8 character length provide different measurements over the same general structure. Vectors, ordered sets/maps and strings have related representations and some constant-cost views. Uniform representation can simplify implementation and make operation costs more predictable across this family; the paper does not measure maintenance effort from that simplification or show that every container workload benefits.

A zipper stores the reverse path from a focus to the root, with a node reference, child index, dirty flag and parent context. Dereferencing the focus is constant time. Local movement goes up to a common ancestor and down to its neighbor; larger jumps traverse more context. Updating the element creates a changed leaf/context and marks it dirty, postponing reconstruction of ancestors. Insertion/deletion restore nearby balance before marking the context. Thus a series of local changes can share reconstruction work. Extracting a complete container unwinds the dirty path in **O(log N)** worst-case time. Copying a cursor preserves both position and its version; it does not duplicate the whole payload.

The paper assigns amortized O(1) costs to local movement/insertion/deletion and O(log N) to indexed access and arbitrary jumps, contrasting the latter with mutable vectors' O(1). Concatenation/splitting improve over contiguous-buffer copying. These are a design analysis based on finger trees/zippers, not a mechanized proof of every implementation path or a uniform worst-case constant-time guarantee. The table mixes amortized and worst-case cases as explained in the text; an O(1) incremental-space entry is not a bound on all retained versions.

**Allocation and ownership are material parts of the design.** Fixed64byte tree/zipper nodes permit a free-list allocator whose zero offsets encode consecutive free blocks. The paper reserves virtual space and relies on demand commitment; the handful-of-instructions example is single-threaded x86-64 assembly, whereas the reported benchmarks run on ARM64. Other allocator modes are described separately. Reference-count uniqueness permits destructive reuse, and packed leaves improve locality. These choices bundle with the representation in the comparisons; no single “persistence tax” can be isolated from the entire implementation by comparing libraries.

The filtering and editor examples illustrate expressive programming patterns. Stateful filtering makes control state explicit; a persistent cursor compactly represents a text buffer plus position for undo/redo. Table1 compares chosen implementations and author-assessed idiomaticity, under a stated strict-semantics simplification for Haskell. It is not an exhaustive lower-bound argument against functional APIs, a user study, or a measured complete editor. [S213](S213-transient-sequence.md) provides a different linear-filter construction with an ephemeral output, trading away the same form of input/output sharing. The released editor also has a concrete backspace mismatch, recorded in the artifact note, so the displayed pair is not an established equivalent application benchmark.

## Evaluation and positive/adverse evidence

The paper reports a **macOS ARM64/M2Pro/32GB** machine, Clang21.1, libc++21, Catch2 3.11.0, Immer0.8.1, Abseil20250814.1 and Folly2025.11.03.00. Source registrations span37sizes from10 to100,000 elements. Vectors stand for sequence containers and sets for node-based containers; strings/maps are not independently benchmarked here. Ordered-tree and hash-set baselines have different additional semantics. The tests use indexed scan, append, indexed update and repeated concatenation, then iterator scan/append/update/erase. The memory section constructs unsigned64bit collections. No retained-history editing session, game frame trace or human maintenance task is reported.

Catch2 means/intervals are extracted by the released plotting script, but the archive has no raw XML/CSV outputs and no calculation tying the caption ratios to exact rows. The paper's “unopt” condition is described as a standard-allocator comparison; the artifact instructions use debug mode, while the source allocator selection is hard-coded. Therefore the inspected recipe does not establish an isolated allocator ablation. The [artifact note](S212-libfpp-artifact-check.md) separates these exact limitations from the unaffected design and reported outcomes. No missing cell is treated as zero, and no author benchmark has been reproduced.

The safety benefit has a precise semantic target: an independently retained cursor version survives changes to another logical version. The paper presents tests and examples, not observed reductions in developer bug incidence, a proof of all C++ memory safety, or a controlled comprehension/repair benefit. Its stated non-goal is replacing STL in performance-critical code. That qualification and the large measured slowdowns should remain alongside the useful interface and concatenation/selected erase benefits.

## Consequence and continuation

For **B01/B04/B06**, this is a substantial predecessor/alternative for making versioned state convenient in an imperative language. Traversal-local updates, deferred reconstruction and sharing can support compact editor state; preserving aliases, choosing when to materialize and selecting operations determine costs. [S211](S211-rrb-systems-persistence.md), S213 and S212 differ in cursor semantics, ownership, representation and retention conditions. None demonstrates an architecture-wide Nu or F#/C# advantage.
