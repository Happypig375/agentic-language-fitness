## Method: executable mechanics inside a larger game

Micro-Machinations (MM) describes a game's internal economy as a graph of resource pools and connections. Resource quantities can represent money, health or experience. Sources generate resources, drains remove them, and nodes pull or push along connections. Passive, interactive and automatic activation have different triggers. An `any` connection policy treats rates as upper bounds and permits independent processing; `all` requires the relevant flows together. Conditions govern activation. A converter expands into consumption, a trigger and production, taking two steps rather than one. Those temporal differences matter to an observation oracle.

Named definitions add modularity. References bind internal interfaces to surrounding resources; input/output directions constrain connections. An instance pool contains local instances with individual state and shared type interfaces. Resources entering or leaving it create or delete instances; instances themselves do not flow between pools. A special `self` pool ending at zero terminates its instance. These are constructive resource/ownership rules, not an assertion that all game objects share one immutable world.

The earlier MM AiR tool is described as supporting simulation and Spin-based analysis. The contribution here is **MM Lib**, a C++ interpreter/library embedded in a running game. Textual modifications change model elements **between evaluation steps**. The host activates named nodes, requests the next step, and receives callbacks/messages about values, definitions and instances. The paper's main examples are visual diagrams, but the implemented editing path uses textual MM. Graphical editors/debuggers and further integration are future work.

The AdapTower prototype is written in **C#**, with a wrapper marshaling calls into C++. Its host physics layer owns positions, speeds, trajectories and collisions; UI actions also activate mechanics. The economy owns the modeled resources and conversion rules. Tables2–4 document named integration points, including notifications for values and instance creation/deletion. The mechanism therefore supplies a prior example of live game-rule adaptation in a .NET host without requiring a general-purpose functional world representation.

## Changes demonstrated and what the report measures

The narrative has a concept stage0 and stages1–6. The initial implementation separates towers, bases and the shared economy. Subsequent changes add experience-dependent tower abilities, base health and heat, experience decay, age-dependent essence amplification, and selectable tower upgrades. These are changes to rules and structure, not merely reloading a scalar constant. New interactive upgrade nodes can be exposed through a deliberately programmed host default that creates clickable names. That is concrete useful extensibility under a convention, not automatic derivation of every new UI or physics behavior.

The authors report **about fifteen minutes per iteration for gameplay design and textual mechanics additions/changes**, followed by brief playtesting that they judged to achieve the desired emergence. They also report that name bindings took a small fraction of implementation time, without a numerical denominator. This is favorable author experience from one evolving prototype. Preserve it as such: there is no controlled non-MM arm, participant/time-log dataset, paired development baseline, defect-rate estimate or player-experience measurement. It does not establish a reduction ratio or statistical significance. The paper explicitly leaves industrial validation for future work.

Table1 gives **expected** activity levels over concept, elaboration, construction and delivery. It is a proposed process account, not observed longitudinal work allocation. The paper acknowledges DSL analysis, notation design, training and language-maintenance cost, and that a preexisting scripting language can be technically easier to embed. Changing a name-binding contract may require new host code. The reported short iterations exclude a measured total budget for constructing the language/library, engine integration and later support.

Mechanics analysis is also scoped. A shared executable model can help compare simulated and embedded economy behavior, but the paper admits that MM need not describe the whole game's runtime. Spatial motion, input timing and host effects remain outside it. The claimed common model does not itself prove end-to-end equivalence, safe arbitrary migration, consistent pending callbacks or rollback of external effects.

The relevant [reflection path](https://github.com/vrozen/MM-Lib/blob/df94e6549baf561e49bb4c3b85934ded5761b27e/mm/mm/Reflector.cpp#L146) merges explicitly supplied named elements. Existing definitions are traversed; omitted elements are not implicitly deleted. A same-kind node replacement preserves the node object but changes its behavior and sends an update notification; changing kinds sends deletion/creation messages. This is an explicit delta mechanism, not an inferred semantic correspondence between arbitrary whole programs.

The [pool update implementation](https://github.com/vrozen/MM-Lib/blob/df94e6549baf561e49bb4c3b85934ded5761b27e/mm/mm/PoolNodeBehavior.cpp#L624) makes the state policy concrete: it computes a delta from the current stored value to the new declared `at` value, adjusts quantities, **sets the stored value to `at`**, and reconnects the expression dependencies. Thus retaining a node's identity does not preserve its previous quantity when that pool is redefined. The displayed value may also include an expression over other pools. This is useful specified implementation behavior, not necessarily a defect; a designer must choose whether such a reset matches the intended adaptation. The inspected functions do not establish whole-change atomicity, rollback or preservation of arbitrary external obligations.

README describes AdapTower as built on Phantom, an entity-component engine for XNA, and states that the graphical MM editor is absent at that snapshot. It gives an explicit text-edit/next-modification workflow. These observations strengthen the account of integration and weaken any inference that the paper demonstrates a complete graphical authoring environment or a purely functional runtime.
