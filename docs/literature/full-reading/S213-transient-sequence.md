## Representation and operation reconstruction

A transient interface combines persistent versions, an ephemeral interface and conversions between them. The opening immutable-array/K-tree account motivates copying costs, then shows how an owner identifier permits a node to be modified only when the current ephemeral structure owns it. Shared paths are copied and retagged. A snapshot revokes prior ownership; the logical values remain stable despite subsequent physical mutation of uniquely owned storage. This requires the identifier/alias discipline, not merely the use of a functional-looking API. Repeated nearby updates can amortize the first path copy, but keeping more roots can preserve sharing and change the cost.

Sek represents a sequence by a front chunk, a recursively defined middle sequence of chunks, and a back chunk. Weights count underlying elements. A nonempty middle requires nonempty ends; its chunks are nonempty; each adjacent pair has combined size greater than K. These density conditions support logarithmic depth without requiring every chunk to be full. Indexing descends by weights. Packed chunks permit constant work per layer; arbitrary relaxed chunks may require a K-sized scan. The implementation uses different capacities at the outer and deeper levels: the evaluated defaults are128 and16.

Concatenation assembles a bounded list of boundary chunks and compacts adjacent pieces while recursively joining the middles. Splitting partitions the chunk containing the requested position and rebuilds the ends. Local K-sized work plus potentially logarithmic end-population work at each depth yields the author's O(K log_K n + log²_K n) bounds. These are actual concat/split methods, unlike a simple tree that only supports point updates. Pure persistent get/set have general O(K log_K n) bounds; packed get and owned packed set can be O(log_K n). Persistent push is generally O(K log_K n), while pop uses views and is O(log_K n), with separate small-sequence cases.

**Hidden monotonic writes** can extend a chunk into an unused support slot outside all existing views. Old logical sequences still observe their old ranges. A misaligned/full support instead requires a copy. Shrinking a persistent view can leave popped elements reachable through its backing support, so logical deletion is not immediate memory release. Ephemeral operations can overwrite freed slots with a supplied default value; that carries an API and write-cost obligation. Concurrent pushes into the same support can race: the paper explicitly leaves atomic support or disabling this optimization as future work. Persistence alone does not make this implementation safe for concurrent updates.

Short persistent sequences use specialized empty/singleton/array forms, reducing the fixed cost of small objects. The threshold is32 by default. The space analysis assumes this optimization at every depth, whereas the described implementation applies it only at the top level. Ephemeral outer front/back chunks are uniquely owned, with extra inner buffers that are full or empty; this removes some indirection/ownership work and prevents a bad alternating end-operation pattern. These are representation and implementation choices, not properties of immutable values in general.

## Guarantees and their conditions

The central amortized result is **O(log_K N) per ephemeral push/pop**, where N bounds the size the sequence may reach. It remains meaningful with shared middle chunks, but **edit must be charged O(K log_K N)** to initialize potential, even though an isolated edit costs O(K). Repeatedly editing a persistent ancestor cannot reuse one initial credit indefinitely. The analysis is not an O(1) worst-case or branching-history guarantee. AppendixB's printed potential has two constant-factor bookkeeping slips; the elementary correction in the artifact note preserves the stated asymptotic order, and is not a machine-checked proof.

Figure16 calls conversion to persistent form `snapshot` and gives O(1) for long sequences. The inspected release has a consequential distinction: **`snapshot` preserves the ephemeral input and costs O(K); `snapshot_and_clear` clears it and is documented O(min(K,n))**, with an O(1) amortized charge only in the specified push-built case. The source copies outer chunks for the former and transfers storage for the latter, which also invalidates iterators. A caller retaining a working editor and an undo version needs the actual API semantics; the figure's conversion row cannot simply be assigned to every snapshot call.

The space bound is for one represented sequence in a stated word-allocation model: OCaml `(2 + 22/(K−1))n + O(K log_K n)` in general, improving to `(1 + 11/(K−1))n + O(K log_K n)` without concat. The C model has12 and6 in place of22 and11. At K=16 the no-concat linear coefficients are about1.733 and1.4. These are neither measured peak RSS nor the joint size of every retained history root, payload graph and collector reserve. Packedness, short forms, ownership and backing-support retention all matter when transferring the claim.

## Validation and measured outcomes

The implementation exposes roughly170functions over four public types, described as about6,000 code and4,000 comment lines. Monolith compares operations against a reference model through type- and precondition-respecting generated programs, including nonlinear sharing between descendants of an ancestor. Optional invariant checks cover chunk/view/owner relationships. The authors report that testing found ownership-related bugs. AppendixA makes a validation predicate concrete; it does not report a campaign budget, fault-sensitivity rate or proof of the entire library. A previously verified transient stack shares ideas; complete Sek verification is future work. The acknowledgement of AI help on merge code is an author process report followed by author review/testing, not a controlled agent-effect result or independent review in this survey.

The performance section explicitly limits itself to **linear stack use without exploiting persistence**: repeatedly push to a peak length n and pop to empty, aiming at100million pushes and100million pops. It uses an AppleM2Max/64GB machine, OCaml4.14.2+flambda, an8MB minor heap, and means of three runs per point. The source confirms CPU-time measurement, setup inside timing, correctness checks during pops, discarded intermediate versions and an integer-rounding normalization limit. No variance intervals or retained-history benchmark are supplied in the read paper/source package.

## Survey consequence and next dependency

For **B04/B06**, S213 provides a concrete alternative with both concat/split and owned mutation, explicit worst-case/amortized/space assumptions, and favorable as well as adverse stack results. Together with [S211](S211-rrb-systems-persistence.md), it undermines treating persistent state as an undifferentiated innovation or a cost-free history mechanism. It also demonstrates that implementation choices can make rich sequence operations practically competitive in a stated workload. That positive result should not disappear behind the transfer limits.

For **B07**, model-based nonlinear testing is relevant to aliasing correctness, but typed traces and successful invariant checks do not establish all semantic, concurrent or temporal obligations. Physical sharing, mutable elements and irreversible effects remain different questions. For a funder, the useful residual is which actual Nu operations, histories and integration obligations would benefit, rather than whether this paper proves an architecture-wide advantage.

**S212's acquired persistent iterators** are the next consequential method: Sek's iterators are mutable, read persistent values and may update an ephemeral sequence subject to invalidation. The related-work section explicitly contrasts an iterator that itself preserves value semantics and returns changed persistent versions. Its filter example is not yet a matched empirical comparison. Read S212's method and evaluation before choosing between those interfaces. Existing retained-history, MapReplay/.NET, practice and type frontiers remain independent; this reading closes no broad-survey theme and authorizes no experiment.
