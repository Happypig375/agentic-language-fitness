## Mechanism, obligations and costs

Store represents an explicitly managed bag of heterogeneous mutable references. A current version stores values directly in the references; older versions point through a tree of undo records toward the current root. A snapshot saves a version node. Restoration traverses the path to the current root, applies changes in reverse and reverses edges/recorded values so the previously current state can later be restored. This follows Baker's version-tree mechanism; persistence need not mean immutable implementation.

The optimization records at most the first write to each location between consecutive snapshots. Store, references, snapshots and log records track **generations**, which identify snapshot separation along a history, not globally unique timestamps. Repeated writes in the same generation avoid additional log allocation. Explicit capture points make this possible; taking a snapshot after every write removes that opportunity. A persistent-interface implementation with transient views can express similar batching, so this is a concrete interface/performance choice rather than a universal imperative/functional dichotomy.

Reads and elided writes have small constant costs; non-elided writes allocate and record state. Restoring costs the length of the relevant logged path. For one consecutive-snapshot interval, the recorded differences are bounded by distinct modified locations; across many intervals, the same location may contribute repeatedly. Repeatedly switching between distant snapshots can repeatedly pay the whole path cost with no new writes to amortize it. The paper explicitly says lockstep evolution of two versions is unfavorable and leaves rebuilding unresolved. An O(1)-amortized restoration argument for one-use backtracking does not extend to arbitrary persistent switching or bound individual restore latency.

The integration contract requires routing all relevant mutations through the store and keeping reference/store identity correct. `store.mli` explicitly warns that using a reference with the wrong store is **unchecked** and corrupts its semantics. Snapshots and transactions have dynamic store/validity checks. Stored values can themselves contain mutable structures; the library does not recursively journal mutations outside managed references. Restoring this store is therefore distinct from undoing file/network effects, callbacks, pending work or every field of a game world. The published prototype has no concurrent restore support or confluence operation joining independent stores.

Memory reclamation follows actual retained paths: forgetting snapshots can release their obsolete log portions, unlike keeping every historical operation in a central journal. But a retained snapshot can keep otherwise forgotten references alive. If an intermediate snapshot is forgotten while earlier/later snapshots survive, its old recorded value can remain reachable even though it can never be restored directly. Record elision does not guarantee minimal retained memory. Transactional commit removes some redundant records, not all possible retention.

## Persistence, transactions and what is verified

Persistent snapshots may be restored multiple times. The semi-persistent API supplies nested transactions terminated by commit or rollback, invalidating the transaction and its descendants. A snapshot taken inside a transaction is valid only until an enclosing transaction terminates. Snapshots can temporarily move execution to a different transaction context and back, provided those dependencies remain valid. The wrappers `temporarily` and `tentatively` encode unconditional rollback and rollback-on-exception respectively; these are sequential state operations, not a concurrent STM service.

The Iris/Coq result verifies the **persistent core with record elision**, in a separate untyped imperative language. The model maps managed locations to values; `get`/`set` require membership in the current model, capture preserves that model and produces a duplicable snapshot assertion, and restore returns the snapshot's model. The proof tracks captured nodes separately from intervening nodes whose models may change through elision. This explains why persistent snapshots remain stable despite internal mutation.

The paper explicitly excludes transaction verification, termination and time-complexity proofs. It establishes acyclicity but does not turn that observation into a verified termination theorem. The matching proof-file hash and selected definitions support artifact identity and the stated interface; they do not certify compiled OCaml correspondence, finite machine-generation behavior, the full runtime or our independent proof checking.

Monolith provides separate model-based testing of the combined transaction/snapshot API. The executable model uses an immutable integer map, transaction dependency lists and termination flags. The pinned harness uses one store, two references created in the prologue, sequential integer values and fuel 60. It declares capture/restore, transaction/commit/rollback and get/set; it does not generate new references during the operation sequence or test heterogeneous values/multiple-store mistakes. Invalid-argument payload differences are intentionally ignored. The authors report finding small counterexamples quickly; their description of an apparent correctness oracle is experience, not exhaustive coverage or a quantified fault-sensitivity estimate. This is nevertheless a useful concrete method for testing stateful semantics outside the proven core.

## Measurements with positive and adverse comparisons

Microbenchmarks vary read/write density, locations touched, snapshot frequency, commit versus abort and nesting. The eight implementations differ in capability: native Ref cannot restore; TransactionalRef supports only nonnested transactions; BacktrackingRef/Facile/old Colibri2 are semi-persistent; Store also has persistent snapshots; Map uses persistent integer maps; Vector copies arrays. The measured Colibri2 is explicitly the older implementation, preceding its January 2024 change toward Store's design.

Appendix C uses one AMD Threadripper 3990X machine, reported 264 Go RAM, fixed 2.2 GHz, hyperthreading/frequency scaling disabled and one isolated core. The authors report controlling code alignment with sixteen variants after observing roughly 10% swings. Figure 6 normalizes to Store, while the appendix tables normalize to their own fastest entry. **All 114 rows across seventeen appendix tables were reconstructed; their center ratios are compatible with the printed time/ratio rounding.** These are author measurements and our arithmetic, not new runs or independent replications.

| Workload / boundary | Reported observation |
| --- | --- |
| Raw, no snapshots | Store 106.6 ms versus Ref 102.9 ms: reported 1.04×. Small overhead, not literally zero. Map 2,664.4 ms |
| Abort, mixed/get | Store leads or ties the other journaled implementations; the get-only table gives all four 97.5 ms at printed precision |
| Abort, write each location once | Vector 70.1 ms versus Store 168.7 ms: Store 2.41×. Copying wins when almost every location must be preserved |
| Abort, sixteen writes per location | Vector 70.7 ms versus Store 78.4 ms: Store 1.11×; elision narrows the gap |
| Abort, sparse large-support capture | Store 93.7 ms versus Vector 568.8 ms, while specialized TransactionalRef leads at 80.6 ms |
| Commit, few writes | Facile 43.7 ms versus Store 58.9 ms, reported Store 1.35×; its speed trades against retention in other histories |
| Deep nested backtracking | Vector 216.9 ms versus Store 273.3 ms, reported 1.26×; this source workload builds one deep chain then unwinds it |
| Store persistent versus semi-persistent API | 413.6 ms versus 275.9 ms, reported 1.50×, in a separate nested-workload comparison |

A separate 10,000-round retention example reports 6 Mo for Store versus 645 Mo for Facile. The distinction is concrete but workload-specific; a full memory distribution/measurement protocol was not reconstructed. Claims that every alternative is always worse would contradict the copying and specialized-journal results above.

The five Figure 7 application comparisons further delimit value:

- **Inferno explicit checking without GADTs:** Store 0.21 s, Vector 0.28 s, Map 0.88 s, reported 1/1.3/4.2 ratios. The large generated term performs no snapshots; native references reportedly match Store in this special case.
- **Small GADT check repeated 1,000 times:** Store 0.02 s, Map 0.08 s, Vector 1.3 s, reported 1/4/70 ratios. The authors explicitly lack representative GADT programs and call this a limit case approaching a microbenchmark. Ratios are not recomputed from the heavily rounded times as if those were exact.
- **Inferno inference with short nonnested transactions:** Store and the purpose-built TransactionalRef both 0.03 s; Map 0.09 s; Vector 1.78 s, reported 3× and 52×. These share Inferno/code and generated-task lineage with the checking studies.
- **Constraint-based well-typed-term generator:** persistent Store 262 ms versus Map 334 ms, reported Map 1.27×. A separate codebase supports a persistent-API use case, but this is a specific author run, not independent evaluation or a population of user programs.
- **One 25×25 Sudoku board:** optimized full-copy baseline 1.35 s, Store transactions 1.63 s, persistent Store 1.76 s, Vector 4.03 s. The baseline remains fastest; the general library costs about 20% or 30%. Compact representation and buffer reuse matter. A separate ref-array substitution reportedly adds 48%, so generic Vector is not the strongest possible copying implementation.

These establish scoped low overhead and sometimes large gains, not measured programmer effort, game-save latency or general adoption benefit. Appendix A's survey of compiler/solver implementations is useful author practice evidence with dated source links; those codebases were not independently re-audited here.

## What the pinned artifact resolves

The benchmark script specifies OCaml `5.1.1+flambda`, release builds, sixteen alignment values and ten Hyperfine warmups. It does not fix a measured trial count. Inlining is deliberately aligned across implementations, and the README describes changes to competitor fast paths. These controls improve the particular comparison but make compiler configuration and modified implementations part of the intervention.

The notebook loads unversioned `results`, `results-colibri2` and `results-redo` directories, preferring redo data where present. It clusters per-alignment run means, sorts each cluster and normally selects its **fastest mean**; it can also show a slow cluster for chosen comparisons. Thus these centers are not averages over all sixteen layouts. Table spreads use within-run standard deviations and propagated ratio errors; the plotted error function only scales the implementation's spread by Store's center. They are not confidence intervals accounting for alignment selection and run/batch correspondence. The pinned README contains older numbers and explicitly allows selective table updates; the notebook has no cached results. Exact data-to-publication binding remains unresolved.

The workload specification also has concrete differences. Published Raw says 32 reads per reference for 1,000 iterations. The pinned script sets `NREAD=16`, meaning 65,536 total reads or 64 per reference, and Raw rounds 800; the raw loop includes both endpoints, giving 801 iterations. The get variant sets `NREAD=18`, giving 256 rather than the printed 128 reads per reference. A zero logarithmic read/write parameter yields **one** operation, not zero. Raw/transaction loops include the final numbered round; nested backtracking stops before it. The appendix itself inconsistently describes default read counts. No actual-run failure or changed ranking is inferred from these source/description mismatches.

The source's backtracking benchmark builds a single chain and unwinds it; it does not repeatedly move between persistent siblings. The README acknowledges this. The term-generator application adds a distinct persistent use case, but costly arbitrary version switching remains a stated limit. No saved raw measurements or application artifacts were recovered from the inspected Store tree.
