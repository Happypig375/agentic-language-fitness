## Problem, inputs and algorithm

CodePlan automates a chain of dependent edits within one repository-level task. Inputs are an initially oracle-valid repository, supplied seed-edit specifications, an oracle and an LLM (pp. 3-6). The contribution is incremental dependency/change-impact analysis plus adaptive planning that infers further edit obligations. This is close prior art for coordinated change propagation and contextualized editing, not an experiment comparing two maintained architectures over successive independent requirements.

Algorithm 1 builds a dependency graph and a DAG of edit obligations. For each pending obligation it extracts the target block and an enclosing-class sketch, adds spatial dependencies and relevant preceding edits, asks the LLM for an edit, merges the result into the AST, classifies atomic changes, updates dependency edges, and enqueues affected blocks. Completed obligations can lead to new pending obligations. Once the plan finishes, oracle errors seed another iteration (pp. 5-11). There is no published general termination bound, fixed call ceiling, retry cap or convergence proof.

The graph covers containment, imports, inheritance, overrides, calls, instantiations and field use. Table 1 gives modification/addition/deletion rules using dependencies before and after the edit. Body changes propagate to callers when escaping objects are affected; signatures can affect callers and overrides, including relations altered by the edit. New classes/imports initially have no assumed users. Static analysis incompleteness remains possible, especially dynamic dispatch/data structures (pp. 7-9, 15, 18-19).

Spatial context includes callees, accessed members, overridden/overriding methods and superclass constructors. Temporal context linearizes root-to-obligation paths, carrying before/after fragments and labeled causal relations (pp. 9-10). The prompt combines task, earlier changes, reasons for change, related code and target block. These are *relevant active edit histories*, not an undifferentiated old observation transcript. Both information type and selection method matter.

## Experiment and outcome definitions

Seven selected tasks comprise four C# migrations (two proprietary, two public) and three public Python temporal edits (pp. 11-12, table 2). Authors choose source/target PR states and seed changes; unrelated edits are applied to both states or excluded, and formatting/style are normalized after initial experimentation. Targets range from 4 to **341 files** in table 2, despite prose stating 4-168. Seed counts range 1-63; derived changes 3-375. The C# prompt-length claim of 81 lines has an Ext-2 table exception of 110. This is a small purposeful collection, not a random task/language sample.

Main model is GPT-4-32k, temperature 0, top-p 1, one sample per edit. Tree-sitter and Jedi support analysis; exact hosted-model snapshot and full effective run settings are not supplied. Oracle-guided Build-Repair/Pyright-Repair use the *same contextualization* but locate edits from compiler/type diagnostics. Pyright strict is an additional baseline. This isolates an approach difference more closely than an unrestricted agent comparison, but planning, localization and propagation still vary together (pp. 11-13).

The evaluation's **validity check requires both no oracle errors and agreement with ground-truth edits modulo formatting/whitespace** (p. 13), with method-order differences also discussed in Ext-1. It is not simply build success, and it is not a behavioral test suite proving all acceptable implementations. Python can have no checker errors while missing required changes. Matched/missed/spurious blocks score edit localization; DiffBLEU and file Levenshtein measure textual similarity, not maintainability. Equivalent alternative solutions can be penalized.

The released metric code intersects source/target/prediction file paths, omitting noncommon files; computes DiffBLEU only when both diffs are nonempty; averages file BLEU and sums Levenshtein. Ext-1/Ext-2 have different diff normalization. Block metrics count separators in supplied annotation files. The package contains reference/predicted outputs and scoring scripts, not the CodePlan planning implementation or the two private repositories. Consequently, artifact inspection clarifies scoring but does not establish end-to-end reproducibility or a behavioral oracle. No source scripts were executed.

## Results, exceptions and arithmetic

Table 3 (pp. 13-15) reports CodePlan validity 5/7 versus 0/7 for oracle-guided baselines. Int-1 and Int-2 need a second iteration to fix 4 and 6 build errors; the prose's unqualified claim of no introduced build errors must be read as final, not first-iteration, behavior. Ext-2 still fails after iteration 2; T-1 misses two edit sites because dynamic dictionary-held classes escape the dependency analysis. The paper explicitly identifies incorrect model edits and incomplete static analysis as failure causes.

Context ablation on five tasks (table 4, pp. 15-16) removes temporal and/or spatial information. Both selected C# tasks fail without either context type. On Python, temporal information is part of the task input and is not ablated; removing spatial context leaves T-2/T-3 validity unchanged and T-1 still failing, while textual similarity worsens. Thus the study does not show that all historical context or all spatial context is always needed. Ext-1 has 64 matched blocks in table 3 but 65 in table 4; preserve that discrepancy.

Alternate-model analysis (table 5, pp. 17-18) yields no validity passes for the three Python tasks using CodeLlama-34B or Coeditor within CodePlan. Coeditor misses arguments/sites; CodeLlama sometimes omits the seed change and sometimes propagates an extra parameter into eight spurious blocks. The approach is not independent of model capability.

Table 6's historical API estimates range $0.3-$32 per task, using then-assumed $0.06/$0.12 per thousand input/output tokens. These are cumulative model-call costs, not current prices, human labor comparisons or peak context. Int-1's 399k input plus 66k output totals 465k, estimated $31.86 before rounding; Ext-1's displayed 100k+17k differs from the rounded 118k total. No comparable baseline cost table, wall-clock distribution, repetitions, intervals or formal paired significance test is reported. The seven tasks support a bounded proof of concept, not a population effect or a C# versus Python causal comparison.

## Consequences for ALF

Withdraw novelty for dependency-driven propagation, chains of edit obligations and conditioning on related earlier edits. Adapt explicit change-impact predictions and an oracle loop conceptually, while keeping future reference edits hidden from candidates. Do not use exact reference-text match as ALF's behavior oracle or infer architectural superiority from static-analysis applicability across languages.

CodePlan supplies a strong rival explanation: an information/localization policy can improve coordinated editing without changing architecture. A future architecture claim therefore needs fixed agent policy and equal task/feedback access; a later policy comparison must be separately specified. Its active-history benefits do not contradict masking resolved observations in a different scaffold. Formal validation, finite control limits and accounting remain ALF responsibilities, not properties inherited by citing this paper.
