# S247 — HistOOry: selected object history and workload-dependent costs

Frédéric Pluquet, Stefan Langerman and Roel Wuyts, *Executing Code in the Past: Efficient In-Memory Object Graph Versioning*, OOPSLA 2009, pp391–408, [DOI10.1145/1640089.1640118](https://doi.org/10.1145/1640089.1640118). Main-agent reading, 2026-10-04: **all 17 pages of the acquired author copy, text and visuals; all 14 figures, examples, sections and 28 references**. No appendix. The final publication's metadata describes 18 pages; this is complete reading of the selected author edition, not certification of an unseen final PDF or execution of the implementation.

HistOOry makes selected fields of existing mutable objects available at earlier snapshots. Its useful result is a language-integrated alternative to copying: historical reads and checked postconditions can reuse field histories without rebuilding an entire object graph. The primary measurements preserve both gains and copying-favorable cases. They do not establish a universal slowdown, whole-execution replay, bounded history memory or a Nu benefit.

## What a snapshot means

Sections 3–4.1 (PDF pp3–5) define **partial persistence**: new versions arise from the latest state, while saved versioned values are read-only. The unit is a field, with object state assembled from its fields. A developer chooses both the fields and the snapshot points. Capturing only consistent completed tree operations differs from capturing every internal rotation; neither choice automatically supplies a complete behavioral or temporal oracle.

A historical read returns the saved value when the field was already selected, raises an exception when selection began after that snapshot, and returns the **current** value for a never-selected field. Figures 1–3 make this concrete: old borrowing/status information can coexist with a subsequently corrected book title and client name. This intentionally mixed-time view is useful, but it is not restoration of the complete historical environment.

A write to a versioned field from a past context raises an exception. A write to an ephemeral field changes its present value. The transcript example actually uses a present output object from a historical query. Thus past execution here means evaluating code against selected historical values; it neither suppresses arbitrary external effects nor rewinds native resources, control stacks, inputs or scheduling. Full persistence, isolated transaction-local changes and direct rollback are absent; §§7.2/8 identify these as limitations or future work.

Deselecting a field stops adding historical states while retaining its old history and overwriting its last state; it can later be selected again. This is a change to capture policy, not a documented operation that frees every version older than a time limit. Snapshot choice, field selection and propagation remain programmer obligations.

## Representation, integration and retention

Sections 4.2–4.3 (pp5–9) use a fat-node representation: a selected field refers to an `HStates` object containing value/version pairs. A global version number advances at each snapshot. The first write in a new version appends a state; further writes in that version replace its latest value. Consequently, snapshot creation is cheap, while subsequent writes, historical reads and retained values carry the cost. The ordinary mode does not log every assignment between snapshots.

Chained arrays use space O(m) for m saved field states, constant-time append/latest access and a historical lookup bound of lg(m)+2. A single cached version/value pair accelerates repeated reads of the same historical version. These bounds concern the data structure; they are not measured upper bounds on GC pauses or frame deadlines. The stepwise memory plot and array-growth peaks make allocation events visible.

ByteSurgeon rewrites Smalltalk bytecodes for field reads/writes. Reads dispatch through the active `Process`, and historical contexts use `PastProcess`; `FullRecordProcess` takes snapshots before every field modification. The process-local browsing mode permits present work in other processes, improving on the earlier Java prototype's global browsing flag. It does not establish multicore transaction isolation or an evaluated race-preserving replay contract. The implementation extends the root `Object` and process interfaces without replacing the VM. Its authors' belief that Java/C# performance could be comparable is not a measured CLR result.

Selecting a class's fields instruments accesses for **all its instances**, including unselected ones. Uninstrumented classes avoid that indirection. Therefore source transparency does not mean zero runtime cost for every unselected object.

Selecting an object's reference field alone preserves historical references, not all changes inside the referenced object. The `Set` example needs propagation into its backing array and into replacement arrays after growth. `defaultFieldsToPropagate` supplies that policy through class extensions; a non-versionable array class avoids instrumenting HistOOry's own bookkeeping. This is a concrete integration obligation analogous to deciding which reachable state belongs in an engine history.

The paper keeps histories in ordinary object space and claims normal reachability-based collection of unused objects and their histories (§4, p3; §7.1, p15). **Our inference from the representation:** reachable history entries can keep referenced past objects alive even after present fields cease to reference them. The paper does not specify or measure a bounded-history pruning policy, prove that dropping a snapshot handle frees its entries, or report long-running retained-heap/GC-tail behavior. Its object-lifetime claim must not be promoted into an established history-window bound.

## Applications and actual comparisons

The three applications reconstruct distinct uses (§5, pp9–11): method wrappers record receiver states at entry/exit; checked postconditions compare selected old/current values using a proxy or explicit snapshot; and planar point location associates tree versions with sweep positions. These are implemented examples and synthetic measurements, not a developer study of learning, debugging success or maintenance effort. Three primitives do not measure ease of adoption. The earlier ALENEX prototype is a predecessor of this implementation, not an independent replication.

Section 6 uses an **iMac, 2.4GHz Intel Core 2 Duo, 2GB RAM, Squeak/Pharo developer image 0.1-101166dev08.11.6**. The plots report per-operation averages at the stated sizes. Repeated-run distributions, raw observations, a pinned source release and frame/GC-tail measurements are not supplied by the acquired paper or inspected author entry.

| Comparison and source | Positive result and adverse/bounding observation |
| --- | --- |
| One integer field, selected/instrumented/snapshotted conditions; Fig7, pp12–13 | Recording cost is approximately flat over the tested history lengths; memory grows in array-allocation steps. Instrumentation alone costs about 2×; selection without snapshots about 5.6–6.7×; snapshotting every update about 6.7–7.3×. These are workload ratios, not a universal overhead bound. |
| Random-treap insertion; Fig8 | Five conditions distinguish uninstrumented, instrumented, selected, operation snapshots and every-change snapshots. The reported largest ratio is about 2.3×, with selected variants close at larger plotted sizes. The curves include insertion/tree work; they do not show constant total insertion time independent of tree size. |
| Saved-field reads and the one-entry cache; Figs9–10 | Mean lookup time grows with history on the logarithmic axis. Retrieving the original 1,000 treap values after additional snapshots is faster with the cache; the authors summarize about a factor of two. The plotted curves are roughly 65ms versus 110ms, not an exact universal 2× ratio or a latency-tail distribution. |
| Stateful versus stateless tracing; Fig11 | Adding receiver history costs about 1.3× relative to the already instrumented stateless tracer. Both tracer curves are far above the untraced baseline. This is an incremental tracing cost, not 1.3× total application overhead. |
| 10,000 random swaps at each collection size, integers or 100-element arrays; Fig12 | HistOOry's average check cost stays approximately flat and eventually beats copying as collections grow; copying wins for small collections. Their exact runtime equivalence, including array comparisons, is not established by an acquired executable artifact. No observed implementation failure or attribution of the full gap to that difference is claimed. |

| Repeated singleton `addAll:` operations; Fig13(b) | Copying is favorable at small sizes, then grows with the receiver while HistOOry stays roughly flat and wins at larger sizes. The different update pattern changes the result. |

The visual distinctions in Figures 8, 11 and 13 are consequential: changing the denominator from baseline execution to stateless tracing, or the operation from bulk insertion to repeated singleton insertion, changes the apparent benefit. The favorable results remain evidence under those conditions; they need neither erasure nor extrapolation to an immutable game world.

## Consequence for Nu and the survey

[S246 Tardis](S246-tardis-managed-history.md), §6 on PDF p14, groups two persistent-object approaches into an order-of-3× runtime account. HistOOry's primary supplies a more specific account: high assignment overhead, lower treap overhead, a tracing-relative ratio, and positive/adverse copying comparisons. These are different runtimes, capture contracts, workloads and baselines from Tardis; there is no matched head-to-head result or Nu estimate.

For B04/B06, distinguish **selected historical field access**, **immutable retained world roots**, and **checkpoint-plus-input replay**. Each needs its own rules for reachable state, effects, retention, observation and cost. HistOOry supplies a strong alternative mechanism and explicit propagation policy. It does not supply successor-code/type migration, complete temporal-obligation checking, arbitrary branching from the past or a tested bounded memory policy.

This addresses the unresolved runtime transfer question after the Smalltalk and modified-CLR methods.
