## Live claim and evidence lineage

B02/B03/B04/B07/B08 ask whether preserving edit and execution history makes live changes correct and inexpensive. S101 supplies a concrete prior mechanism: represent design and runtime state in a common graph, record both editing and execution as operations, and reconcile them through version merging. S100 subsequently adds current-state model checking to this lineage. S86's schema-operation work addresses related but different data-evolution problems; these are not independent replications of one effectiveness claim.

The 2023 conference predecessor (`10.1109/MODELS-C59198.2023.00067`) omitted read-after-write dependencies. This journal article explicitly corrects that omission: tracking only overwritten values misses conflicts between a computation and a concurrent edit to data it read. The graph/versioning core is described more fully in a different 2023 article, now S108 (`10.1016/j.cola.2023.101221`). That core predates this read-dependency extension. Preserve the versions when assessing correctness or implementation reuse.

The evidence here is a worked burglar-alarm finite-state-automaton example, an independent-regions Statechart illustration, a web prototype and informal reasoning. There are no participants, comparative maintenance outcomes, latency/memory benchmark or measured language-porting costs. The authors label conflict-free runtime correctness as a hypothesis in §1.1 and give an informal causal argument in §6. They do not supply a general mechanized proof or validate arbitrary language integrations.

## Representation and merge mechanism

The runtime graph embeds the design graph, with runtime-to-design links permitted and the reverse direction excluded. In the alarm, the design contains states/transitions and the runtime adds a current-state pointer. Metamodels are assumed fixed; reflective languages are out of scope. User edits, interpreter execution steps and direct runtime interventions (“god events”) are distinct actions recorded through the same mechanism.

The graph uses immutable node identities, primitive values and labeled outgoing edges. Each edge initially targets null; changing a value or link is an edge update. The primitive operations are node creation, node deletion and edge update. Their dependencies include creation of referenced nodes, overwritten edge values, values read during computation and ordering before deletion. Transactions combine primitive operations; dependencies and conflicts are derived across these groups.

Table 2 lists five conflict cases: source/deletion, target/deletion, two deletions of the same node, competing overwrites, and an overwrite concurrent with a read. Conflicts are detected eagerly among operations with a common dependency. A version groups nonconflicting operations; replay must respect their dependency order. Merging takes their union when possible, or exposes alternative maximal nonconflicting subsets for a user to resolve. **Maximal does not mean uniquely intended or minimum-cost.** The full treatment of dependency closure and conflict-selection rules remains a reason to inspect S108; S101's short definition is not a substitute for that core method.

The ordinary examples distinguish independent changes from shared targets. Adding a state while removing an unrelated state can merge. Adding transitions to a concurrently deleted state cannot. Two actions assigning different current states conflict. Two Statechart regions may advance independently only when the relevant reads and writes are disjoint under their semantics. A shared graph representation alone does not establish independence.

The initialization handler in Listing 2 explicitly records a read of the design's initial-state edge when writing the runtime's current-state edge. Changing that initial state concurrently therefore becomes a conflict. This is a substantive semantic condition, not merely more edit bookkeeping. §6.1.1 states that write dependencies are automatic but read dependencies currently require manual handler annotations; forgotten reads can make merging unsound. Automatic capture using a restricted transformation language is future work. General-purpose handlers may also depend on globals or nondeterministic behavior outside the recorded graph.

## Two live-continuation contracts

The alarm's initial state can be deleted after execution has moved elsewhere. That edit exposes a choice rather than one universal correct migration:

| Contract | What happens to the earlier trace | Remaining boundary |
| --- | --- | --- |
| Recorded-event reconciliation | Treat the edit as concurrent with execution and merge only when the recorded operations remain compatible. Deleting a state needed by initialization conflicts. | The reachability argument depends on valid execution steps, complete dependencies and represented inputs. It does not establish every future behavior or an arbitrary user-injected state's reachability. |
| Current-state (“real-time”) reconciliation | Permit a runtime-specific variant of the deletion with an added ordering dependency after the execution step; retain the original design delta separately. | Execution can continue even though its old trace cannot be replayed on the updated design. The retained state may be unreachable from the new initial model. “Real-time” here names a migration policy, not a proved deadline guarantee. |

Figures 14 and 16 show the override relation and a `design!` indicator for the second case. The design remains independent of any one execution while a particular runtime version carries the extra ordering. This is useful explicit provenance. It does not invent a new valid initial history or resolve every intended-state choice. A successful merge and a successful behavioral migration therefore require separate reporting.

**Review inference:** recorded graph operations cover the represented model. Replaying an edge update is not evidence that external I/O, clocks, native handles or irreversible actions have been restored. A god event can deliberately place the runtime in a state the interpreter would never reach. Claims about replay reachability need those boundaries stated. The paper's causal correctness argument also requires all causes of a step to be represented; its own manual-dependency limitation makes this a live verification obligation.

## Costs, integration and proposed extensions

The abstract presents extra collaborative/debugging capabilities as arising without separate mechanisms. This is an architectural reuse claim, not zero total cost. §6.1.1 requires an encoding, action handlers and UI integration for each language. It says porting an existing language/interpreter currently has complexity comparable to rewriting it. An attempted transparent JavaScript-object layer failed. That is a material counterweight to the earlier claim that encoding is easier than maintaining language-specific reconciliation functions; no comparative effort data resolves it.

The paper states constant-time dependency computation and typically small conflict neighborhoods. **Review inference:** these statements do not establish constant cost for an entire execution step or edit: a transaction can contain many operations, and read/deletion dependencies can have variable fan-out. History storage, graph reconstruction, alternative merges, synchronization and UI costs are unmeasured. Do not turn shifted work before merging into a demonstrated net speedup.

Compilation/code generation is an extension requiring incremental source-to-target transformation and a versioned correspondence model. Figure 18 describes the intended composition; it is not an implemented compiled-language evaluation here. Branch reduction depends on correctly recorded reads/writes: false positives reduce useful independence, while false negatives permit invalid merges. Serialization enables transfer or persistence of represented operations; multi-organization management and access control remain future work. The implementation still has three separate structures for graph state, operation dependencies and version history.

**Unique:** generic operation-based reconciliation of edits and interpreted runtime state has explicit prior art, with a documented dependency correction. Nu-specific distinctions and priority remain unconfirmed. **Valuable:** the policy and conflict information could help a developer choose a live-continuation workflow; benefit, integration effort and net costs remain unmeasured. **Scientifically valid:** validate complete dependency capture, represented-state/input boundaries, trace reachability, override policy and external effects separately, and count rejected merges and integration costs.
