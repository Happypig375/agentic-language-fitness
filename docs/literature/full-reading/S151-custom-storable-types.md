## What the extension establishes

Replacing every mutable field with Store.Ref can be intrusive and can duplicate a mature data-structure implementation. It also forces the same restoration policy onto logically important contents and incidental representation changes. S151 instead lets implementers wrap a mutable structure and supply descriptions of changes that can be undone and, for persistent snapshots, redone.

The relevant equivalence is **logical state under the structure's interface**, not bit-for-bit restoration. A growing array may restore its elements and length while retaining the larger backing allocation. A watched-literal structure may deliberately preserve internal ordering optimizations. These choices require a specified abstraction boundary; keeping such implementation state is compatible with logical rollback only when the exposed behavior remains correct.

An anti-operation records how to return from the resulting state to the prior state. Operations and anti-operations can have different types; for example, initialization carries a value while undoing initialization need not. Composing anti-operations can compress an intervening operation sequence. The classification depends on the chosen operation set and representation of undo information, not just the name of a data structure.

| Interface | Required information and behavior | Consequence |
| --- | --- | --- |
| Free | Supply an operation and its inverse; log every operation separately | Simple and general logging, with no per-object record elision. A rarely written reference can avoid a generation field, but frequent writes grow the log |
| Absorbing | Capture enough information before the first change to undo any allowed continuation; supply rollback and persistent undo/redo callbacks | Later writes in the same generation can be elided. A push-only array needs its old length; persistent undo additionally saves the removed suffix |
| Custom | Supply a mutable trail, its composition, rollback and paired undo/redo; update the trail on every relevant modification | Supports cancellation or summaries that are neither a full old state nor an uncompressed operation list; correctness and cost depend on these user implementations |

The paper writes the absorbing rule as `a.b = a` for composable anti-operations. Its substantive requirement is that the earlier captured information remains sufficient after later permitted updates. It is not a proof that an arbitrary callback of the declared OCaml type satisfies that requirement. A counter can use either summed increments or a saved old value; these lead to different classes. Adding pop to a push-only array likewise changes what must be recorded.

For the custom push/pop example, the trail tracks the shortest unchanged prefix and the removed suffix. Pushes above that boundary require no extra information; popping into the prefix lowers the boundary and preserves the removed element. On commit, a trail from an inner transaction can be combined with the preceding trail. Store must retain a pointer to that earlier trail to do so. This **weakens S150's reachability economy**: a snapshot can retain older undo information that the original reference-only implementation would not need. Weak pointers are discussed as an alternative, not implemented and evaluated here.

The callbacks are semantic obligations, beyond calling `modify` with well-typed arguments. Absorbing/custom users must call it before mutation; custom users must preserve the trail's origin and update its final-state description. The source specifies that redo reuses the physical trail associated with its earlier undo, and append consumes the second trail. Arbitrary callback time, suffix copying and trail merging prevent carrying S150's reference-operation constant costs over to every custom structure. Unrecorded mutation, external effects and pending work remain outside an automatic restore guarantee.

## Evidence and implementation correspondence

The paper's main evidence is a design developed through implementations of references, counters, arrays, sets/maps and watching structures. It explicitly declines a benchmark evaluation of the generic interfaces. Page 15 nevertheless reports approximate reference slowdowns of 20% through Absorbing and 40% through Custom, attributed mainly to indirect calls; page 7 mentions about 20% gains for the semi-persistent API in some uses. These are scoped author observations without a new protocol, trial counts or uncertainty, not independently reconstructed measurements. The earlier S150 microbenchmarks do not validate this extension's generic overhead or integration effort. Adoption into Alt-Ergo is described as a goal, not completed deployment evidence.

The pinned source supports the central mechanisms: generation checks, paired operation/anti-operation edges, parent trails, commit-time append, push-only length capture and custom array/key-value implementations. It also bounds the usability claim:

- The generic `Free`, `Absorbing` and `Custom` modules exist internally in `store.ml` but are absent from the public `store.mli`. The exported interface exposes particular structures. Thus the inspected branch does not itself provide the generic external API exactly as printed. `src/custom.ml` contains only a license header, and the README still says custom structures are planned.
- Callback names and array representations differ from the paper. The source custom array uses an array-valued suffix and clears/reconstructs its trail during undo/redo; the paper illustrates a list-valued suffix retained through undo. Both are allowed design strategies, but they are not identical implementations or cost accounts.
- Some examples remain inconsistent: the PDF's persistent-environment update on page 8 assigns a snapshot to the `store` field rather than the declared `snapshot` field; its page-13 redo example omits the trailing argument required by the preceding signature. These are visible transcription/interface discrepancies, not executed program failures.
- The branch's watcher example compares `active` with list patterns although the public interface and implementation return `WatchSet.t`; watcher creation also carries an unresolved detach-recording comment. These facts limit treating the example as validated. A comment alone does not prove that every custom operation or commit path is broken.

The full Monolith harness defines an immutable map/array model plus transaction dependencies and declared operations for references, hash tables and arrays. However, the active prologue creates **one store and one dynamic array**; reference and hash-table declarations are commented out, with no generated constructors to supply them later. Active array operations cover length, valid-index get, add-last and pop-last alongside capture/restore/commit/rollback, with sequential integer values and fuel 60. Watching structures have model sketches but no generated active bindings/operations. Invalid-argument messages are ignored when comparing exceptions. This is a concrete oracle design and a narrower active configuration than “all representative custom structures tested.” No run outcome is claimed. The S150 persistent-core proof is not a proof of these new callbacks, custom transactions or the complete OCaml extension.

## Closest practice checked against the cited source

The paper contrasts persistent Store snapshots with solver trails that primarily support stack-disciplined rollback. The bounded source check preserves that useful distinction while narrowing broader descriptions:

- [Choco StdSet](https://github.com/chocoteam/choco-solver/blob/758489f2dcf6e9da0fbc3667552f2de4c59277b8/solver/src/main/java/org/chocosolver/util/objects/setDataStructures/StdSet.java), all 166 lines: successful add/remove and each element of clear save inverse operations through `IOperation`, with pooled operation objects. This corroborates the per-operation strategy for this structure, not every Choco data type.
- [Z3 trail.h](https://github.com/Z3Prover/z3/blob/2880ea39/src/util/trail.h), all 426 lines: specialized undo implementations sit under a generic virtual `trail::undo` interface; `trail_stack` accepts trail pointers or templated trail objects and reverses them on scope pop. Thus the paper's “no generic interface” wording must not become a claim that Z3 has no extension mechanism. This file supplies generic operation logging, without the Store-style persistent redo and custom per-object composition protocol.
- [cvc5 context.h](https://github.com/cvc5/cvc5/blob/92caabc77cf8b347cadf1517c75b2af2357d419c/src/context/context.h), lines 18–125 and 300–430: push/pop, subclass save/restore, `makeCurrent` before changes, destruction and allocation obligations are explicit. Its scope wrapper addresses exceptional/early exits but calls its own consistency check approximate. This is established generic contextual rollback with substantial lifecycle duties.
- [cvc5 cdhashmap.h](https://github.com/cvc5/cvc5/blob/0570e78fb972e53e0b39cb29718f2a329bff613a/src/context/cdhashmap.h), lines 15–85: the cited complexity warning is explicitly dated **26 May 2010** and followed by several lifetime scenarios. It is dated implementation evidence, not proof of a current cvc5 defect rate or a measured maintenance penalty.

No whole solver, related publication, full cvc5 file or current release is claimed inspected by these checks. The earlier Store, Inferno, Alt-Ergo and semi-persistence references remain their existing evidence classes or conditional dependencies; this reading does not promote every bibliography entry.
