## Intervention and measurement contract

Sections 2–4 explain low-polygon models, merging vertices, sharing texture/material palettes, baked occlusion culling and object pooling. The two Android-targeted 3D shooting-game versions vary these techniques together. Some shadows are also disabled in the optimized version (§5.2.1). Geometry differs substantially: for example, the sand asset has **2,512 versus 130,050 triangles** and an enemy **3,296 versus 25,585** (Table 1). Asset pictures illustrate appearance; no perceptual-equivalence study establishes equal visual quality.

The pool creates and disables **100 enemies at startup** (§5.1.3). Enemies are subsequently activated/deactivated for reuse, while the comparison uses `Instantiate`/`Destroy`. The maximum simultaneous enemy count is 100 and spawning occurs every half second. Three enemy types share a model but use different textures. The pool's complete reset contract, exhaustion policy and source implementation are not supplied; deactivation is not proof that all gameplay state is correctly reset. This technique retains reusable current objects, not immutable game history or prior running-program versions.

The computer profiler stores the last **900 frames**. Loading uses the large scene-transition spike. Gameplay uses, separately for each version, **the lowest-FPS frame and a frame near 60 FPS**. These are selected snapshots, not a frame-time distribution, matched event trace or random sample. The paper initially mentions a remote phone connection, but §5.3 explicitly identifies the preceding analysis as computer performance and then describes a separate phone test. Figures 10–13 show **Playmode** profiling. Do not transfer their CPU/memory values to the phone.

The actual phone is a **Xiaomi Mi Note 10 Lite**, reported Snapdragon SDM730 octa-core up to 2.2 GHz, 6 GB RAM and 64 GB storage. A script displays FPS averaged over an interval whose length is not supplied. The paper does not identify the actual Unity release, managed backend, garbage-collector mode, operating-system build, computer hardware, run ordering, repetitions, thermal controls or complete recorded duration. Its differently versioned documentation references do not establish the runtime used. These limits constrain transfer and uncertainty estimation; they do not erase the observed within-game improvement.

## Positive results and retained costs

| Observation | Source-located result and scope |
| --- | --- |
| Computer loading | Figures 10–11 show both scene-transition spikes; the optimized trace has fewer large subsequent spikes. Table 2 gives **175.4k versus 734.8k triangles** and **103 versus 109 draw calls** at the selected loading frame. This is consistent with a substantially lighter rendering workload, not an isolated managed-allocation effect. |
| Computer gameplay rendering | The selected lowest-FPS frames have **490.3k versus 3.5M triangles**, **227 versus 248 draw calls**, and GPU buffers of **37.2 versus 95.4 MB** (Table 4, optimized first). Near-60-FPS frames show the same broad geometry/buffer direction (Table 5). The selected frames need not contain identical visible enemies or viewpoints. |
| Computer memory | At the selected lowest-FPS frames, total used memory is **0.93 versus 0.99 GB**, system used memory **1.81 versus 1.98 GB**, and managed heap used **19.0 versus 17.2 MB** (Table 6). At the near-60-FPS frames, managed heap used is **16.4 versus 17.7 MB** (Table 7). The optimized version does not uniformly reduce every memory category. Profiler-used memory itself is approximately 0.58–0.61 GB in these gameplay snapshots. |
| Retained objects | Table 3 gives startup GameObject counts of **5,413 versus 450**; Table 6 gives gameplay counts of **5,458 versus 2,097**. The authors connect higher retained counts to pre-created enemies. Counts include their constituent objects and are not counts of 5,413 enemies. Retained storage and allocation traffic must be distinguished. |
| Allocation observations | Figures 12–13 show fewer allocation spikes in the optimized trace. Table 6 nevertheless records **nine allocations / 506 B versus six / 384 B** in the selected frames. A frame allocation, live heap size and a collection pause are different measurements. The paper supplies no collection-pause distribution or allocation-rate estimate that isolates pooling. |
| Phone startup | Figures 14 and 17 display **59.96 versus 52.13 FPS**. They are screenshots at startup, not a startup-time comparison. |
| Phone action | The authors report **50–60 FPS** throughout optimized gameplay versus **20–30 FPS** during action without the bundle. At 52 eliminated enemies, Figures 15/19 show **56.45 versus 22.15 FPS**; optimized Figure 16 shows **52.01 FPS** at 72 eliminations. Non-optimized Figures 18/20 show **24.58 / 24.52 FPS** at 19 / 75 eliminations. Those scores are cumulative eliminations, not active-enemy counts or matched frame identifiers. |
| Low-load comparison | The non-optimized version returns to **50–60 FPS** when few or no enemies remain (§5.3.2). Preserve this workload dependence alongside the favorable action result. |

The phone evidence establishes a practically relevant reported difference in this game. It does not identify how much came from pooling, simplified meshes, culling, material changes or their interactions. The authors explicitly describe collective testing and propose isolated techniques and frame-rate consistency as future work (§6). The claim of smoother user experience is their interpretation of FPS observations; no player study or maintenance-effort outcome is reported.

## Printed discrepancies that affect interpretation

The rendered tables confirm that the following are present in the publication rather than extraction mistakes. Table 3 prints **6,084 / 0.9 B** for optimized loading allocation and **234.7 MB** of materials against **245.8 KB** in the comparison; the text's claimed 1 MB reserved-memory difference disagrees with **0.88 / 1.08 GB** in that table. Section 5.2.2 says total used memory is 0.93 MB, whereas Table 6 prints **0.93 GB**. Its stated 60.3 MB graphics difference also disagrees with Table 6's **66.1 / 128.5 MB**. Table 7 prints **199 / 57.3 KB versus 7 / 424 KB** for frame allocations. The graph images do not expose sufficient selected-frame detail to repair these entries confidently.

Do not silently correct units, derive precise allocation/memory effect sizes from suspect entries, or interpret the authors' heap-usage explanation as a measured GC invocation rate. These local problems leave the phone FPS screenshots and the broad geometric-work reduction available as scoped positive evidence. The paper's instruction about dynamic occluders/occludees is not used here as authoritative Unity API guidance; actual engine semantics require a separately versioned primary check.
