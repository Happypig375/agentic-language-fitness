## Mechanism and actual comparison

Reactive Inspector makes REScala's dynamic dependency graph available for stepping, node breakpoints, value inspection, history queries and per-node profiling. The Eclipse/Scala debugger still controls execution and supplies values. Logged graph events support backward inspection; this is not a demonstration that arbitrary external effects can be reversed. Sections 4-5 illustrate missing dependencies, expression errors, excessive graph growth and redundant reevaluation. Declarative propagation moves work into a runtime whose behavior must remain inspectable.

The **preliminary questionnaire has 89 students**, of whom 21 reported trying a conventional debugger on a reactive program. It collects preferences and requirements, not measured debugging effectiveness. Thirty-six supplied open responses; 14 explicitly requested dependency visualization. Agreement with suggested graph features is distinct from spontaneous responses and from the later experiment.

The **controlled comparison has 18 fourth/fifth-year CS students, nine per group**, already exposed to Scala reactive programming and Eclipse. Both groups debug reactive programs; the intervention is conventional debugging versus Reactive Inspector, not functional versus imperative source. The paper describes a between-subject design but does not specify a random assignment procedure or a detailed group-balance analysis. Both receive an assisted tutorial of about 30 minutes; the Inspector group receives its manual in advance. Prior RP experience varies.

Figure 16 specifies six authored applications of 44-507 nonblank, noncomment lines: simulation, fisheye animation, synthetic network, Pong, RSS reader and shapes animation. Four tasks ask behavior/comprehension questions, with multiple subtasks; only tasks 5 and 6 ask for bug fixes. The tasks suggest relevant Inspector features. Pong asks for values at particular scoring/bounce events, directly illustrating a temporal observation obligation. Task 5 uses provided tests; task 6 ends when the animation runs without exceptions, a narrower criterion than complete behavioral correctness.

Participants think aloud and staff encourage further work when an answer is incorrect. Tasks were chosen to be completable within the available time. Consequently the endpoint is supervised time to the specified completion criterion, not autonomous success under a fixed allowance or independently held-out regression coverage. The six applications and repeated participant observations are not 108 independent trials.

## Results, adverse cases and reconstruction limit

The reported total-time means are 4,317.33 for conventional debugging and 2,572.67 for Inspector; the reported two-sided Mann-Whitney comparison has `p=0.001`. Transcription of the visually checked Figure 17 and summing its 18 participant rows reproduces these means and the per-task mean pattern. This checks published arithmetic, not the collection of timings, assignment or experiment.

Reported task comparisons favor Inspector significantly for tasks 1, 3 and 4, but not 2, 5 or 6. The mean for task 6 is slightly higher with Inspector. The authors' think-aloud explanation identifies a practical limitation: graph nodes retain names from creation, while source code often refers to them through differently named parameters. Their restricted task-2 subtask analysis is an explanatory follow-up, not a new independently allocated test. Neither a nonsignificant task nor a promising subgroup establishes equivalence or a general benefit.

The paper does not provide a prespecified multiplicity plan, a representative task sampling frame, independent industrial validation or a scalable logging-cost evaluation. It explicitly leaves efficient implementation and broader asynchronous/event-correlation support outside the demonstrated scope. Useful histories also require storage, instrumentation and navigation; they are not free consequences of a functional notation.

Two bounded printing issues are retained without invalidating the study: Figure 17 labels its fifth task column `T1` although Figure 16 and the narrative identify task 5; the task-5 discussion prints `p=0.94` while calling it near significance. No corrected inferential value is invented. Figure 6's left axis identifies Q4 while its caption calls it Q2. The main qualitative inference rests on the stated design and full result pattern, not those labels.

## Artifact and follow-up

The [author project page](https://guidosalva.github.io/reactive-inspector/) and [repository](https://github.com/guidosalva/reactive-inspector/tree/769a17b6c04682bdffebfee2482889d6f2ec0d81) were inspected for provenance and available material. The complete, untruncated master tree has 225 entries at that pinned revision; the `gh-pages` tree has 45 at `96efd18088d9e12b8a876367eb35da6a82955d74`. README, branch/tag metadata and file inventories were inspected. These two trees expose code and example documentation but no identifiable experiment timing dataset; other branches, earlier history, the two example PDFs and embedded video were not fully audited. The paper's public-data statement therefore remains an acquisition gap, not a verified absence everywhere. No plugin was installed or run.

The project page identifies *From Debugging Towards Live Tuning of Reactive Applications*, promoted as S56 because it bears directly on Nu's live-edit/reload claims. Exact-title Scite search returned zero; the six-author LIVE 2018 paper was verified through the author PDF and workshop record, so missing indexing does not erase the predecessor. S49 remains the more directly comparable reactive-tool user study. Older omniscient debugging, managed-time and object-centric work is already explicit prior art in sections 7-8; reopen those methods if a proposed contribution depends on a specific novel replay mechanism.

**Unique:** graph-based reactive inspection, history queries and temporal game observations have clear predecessors. **Valuable:** this study supplies bounded human time evidence for a tool, plus adverse naming cases; it establishes no Nu or coding-agent effect. **Scientifically valid:** retain common tool opportunity for the D1 source assignment, or separately name and evaluate a tool intervention. Do not label a debugger-enabled outcome an isolated architecture effect, or import supervised completion timing as fixed-budget success. Allocation remains zero.
