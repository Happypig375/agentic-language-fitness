## Mechanism and evaluation unit

Pure Arrowized FRP separates signal computation from input/output and time sampling. Reproduction requires the same initial computation, complete inputs, sample times and relevant architecture assumptions. Figure 1 deliberately demonstrates that identical starting conditions with different sampling can yield different stable graph layouts through numerical integration. A functional language or persistent state alone does not provide the claimed guarantee; Section 6.2 explicitly excludes faults in the input/output layer.

The contribution combines temporal predicates, random input/time generators, causal runtime assertions and a remote debugger. It supplies an extended Yampa execution loop and a GUI with synchronous command and asynchronous event sockets. It records/replaces samples, navigates a trace, stops at assertions, and replays after code changes. The described hot-swap process recompiles and restarts the game before replaying its input; it is not arbitrary state migration between code versions.

Section 8 distinguishes forward-only signal evolution from navigation supported by retained intermediate signal functions, for which it claims constant-time random access. Input-only recording instead permits deterministic recomputation. Neither statement demonstrates bounded memory for an indefinitely retained history or a portable snapshot of all external resources. S48's time-reversal operators are a different mechanism.

The evidence consists of capability demonstrations, generated counterexamples and author experience with Yampa, Haskanoid and commercial mobile games. The mobile extensions and commercial use are disclosed as work of the first author's company. There is no assigned human/agent comparison, representative defect denominator, independently measured maintenance effect or runtime-overhead evaluation.

## Temporal and sampling boundaries

Conceptual signals use continuous time; executable tests supply a finite sampled stream. A temporal predicate is evaluated at the initial sample, with future samples addressed by temporal operators. `Always` and `Eventually` in this encoding include the current point, unlike the strict variants introduced earlier. Causal runtime monitoring uses past-oriented accumulation; future-looking predicates require a completed trace or another evaluation policy. Passing the sampled trace does not prove an unobserved future or behavior between samples.

The paper illustrates a falling/bouncing ball that passes a short trace but fails a longer or differently sampled one. A 60 Hz test passes one hundred generated cases, then a displayed expanded run finds a failure after 897 cases. The Haskanoid example passes one hundred cases near 25 FPS but later fails after 3,443; a velocity predicate finds another displayed counterexample after 67. These are individual author-reported runs, not detection-rate estimates or independent benchmark trials. The proposed speed cap is explicitly an ad hoc repair, with continuous collision detection identified as the more general alternative.

Generators choose values, time-delta distributions, bounds and trace lengths; clipping/concatenation can append random continuations to real-user prefixes. Those choices determine what a test can reveal. More realistic timing can require longer traces to reach an event, while unrestricted random timing can create implausible cases. The paper leaves input-space coverage and further shrinking strategies open.

Two printed definitions require caution before reuse as an oracle. The rendered `until` equation on page 8 puts the future-time constraint in an implication under an existential quantifier and omits a lower bound on the inner history interval. Read literally at any time after zero, a witness earlier than the query time makes that implication true even when both predicates are always false. This is a counterexample to the displayed equation as a definition of the intended operator, not an executed defect in a released evaluator. Page 17's illustrative assertion logger uses `when v1` while its example passes a property expected to hold and its prose describes logging violations. The direction therefore conflicts with the prose. Other snippet type/name inconsistencies reinforce that these printed examples are not independently validated executable code. S47's precise definitions and evaluator remain a consequential follow-up.

## Costs, adverse cases and Nu implications

Sections 9 and 6.1 make several costs explicit. Propagating assertion outputs through pure types can require changes throughout the call structure; a debugging monad changes that instrumentation boundary. Logging may slow sampling enough to hide a failure. Input-only logging is offered as mitigation, with no measured overhead or guarantee that it preserves the uninstrumented failure distribution. UI changes may invalidate low-level recorded inputs; higher-level action recording is proposed for future work.

**Unique:** functional whole-game replay, temporal assertions, generated trace continuations and replay across recompilation already have a close predecessor. The paper itself acknowledges deterministic journaling in imperative games and other replay systems. Broad novelty for those mechanisms is untenable; a particular Nu lifecycle/convention contrast remains unconfirmed. **Valuable:** reproducible counterexamples and observation of lifecycle obligations are plausible benefits, while net effort, adoption and Nu/agent transfer remain unmeasured. **Scientifically valid:** preserve sample schedules, input/effect boundaries, trace compatibility, property histories, unsuccessful cases and instrumentation costs. Source equivalence and independent behavioral oracles still need validation before any experiment. Allocation remains zero.
