## What was demonstrated

The authors built an Active Expression (AE) toolset in Lively4 and adapted it to signals and implicit layer activation. Code annotations, a hierarchical overview, event histories and dependency graphs share infrastructure. This is close prior art for integrating reactive mechanisms and their inspection tools. It is not a controlled estimate of programmer productivity, game maintenance or Nu benefit.

The requirements are based on selected challenges from author experience. Usability is argued through walkthroughs, feature comparison with Reactive Inspector and answers to six context-oriented debugging questions. Section 6.3 expressly leaves empirical usability and runtime/memory measurement open, despite performance appearing in the introduction's contribution list. Similarity to an evaluated tool does not transfer that tool's measured effect. S43, S46, S49 and S60 retain their separate completed scope; citations to them are not new replications.

The implementation illustrates both reuse and its boundaries. Adapting a shared implementation requires knowledge of its internals and preserving other concepts' behavior; a stable extension API is future work. The paper favors direct modifications to retain flexibility. The result therefore cannot justify a generic plug-in architecture or a new Nu instrumentation framework without a separately scoped need.

## Controls and adverse cases relevant to Nu

| Issue | Actual mechanism and implication |
| --- | --- |
| Automatic dependencies | The abstraction tracks executed accesses, but section 3.1.2 documents missed loop-condition accesses and uninstrumented external/native code. The general claim of eliminating missed dependencies must be bounded by instrumentation coverage. A dependency graph is an observation of that mechanism, not an independent behavioral oracle. |
| Atomicity and glitches | The linked-list example reacts to an intermediate length update before an insertion completes. Ordinary method-level assumptions can fail when instrumentation crosses abstraction boundaries. Signals impose their own ordering/cycle constraints; arbitrary AE callbacks and mixed concepts do not inherit universal glitch freedom. |
| Lifetimes and edits | AEs require explicit disposal. Old instances can survive repeated live edits and continue producing effects or retaining objects. This is a concrete lifecycle obligation for any claim that live modification or functional organization simplifies maintenance. |
| Error visibility | The described AE system catches evaluation errors; the tools make them observable. A lack of callbacks, a logged error, a restored state and correct public behavior must remain distinct outcomes. |
| Selective history | Equal-result reevaluations are deliberately unrecorded, dependency changes are accumulated, and event recording is controlled per file. Recording defaults off except for changed files or explicit activation. The absence of an event cannot automatically answer why an expression did not react. |
| Observation versus restoration | The history view reconstructs selected graph/event information. It does not establish whole-program snapshots, effect reversal or complete external-state restoration. The described stack copy is shallow; this paper does not prove general snapshot fidelity for arbitrary mutable values. |
| Always-present cost | Disabling recording limits some history storage, but the paper explicitly identifies rewritten debugging annotations as a cost even when a tool view is closed. Runtime, memory and rendering responsiveness remain unmeasured. Author experience of no visible lag is not a benchmark. |
| Environment coupling | Lively4's program and tool UI share a thread; breaking execution also freezes the tools. The chosen history-oriented workflow reflects that constraint. A future Nu comparator must preserve the actual tools available, rather than assuming every debugger feature coexists. |

Appendix B makes the remote editor's evidential scope particularly clear: storage is a local `Map`, server availability is supplied by a checkbox, and the remote-change callback is a stub. It illustrates interactions between signals and method layers, not synchronization over an actual unreliable network or validated distributed recovery. No new runtime defect is claimed from the printed example.

## Three criteria and follow-up disposition

**Unique:** reusable reactive inspection, implicit dependency visualization and shared histories across concepts are established. An engine name does not make those mechanisms new; a narrower Nu comparison remains unconfirmed. **Valuable:** tool reuse and source-linked inspection are plausible advantages, accompanied by disposal, instrumentation, integration and learning costs. No net user or agent benefit is measured here. **Scientifically valid:** account for instrumentation and implementation cost, preserve unchanged reevaluations and missing observations where consequential, test lifecycle/effect boundaries, and distinguish source size from maintainer effort. No apparatus or experimental allocation follows.
