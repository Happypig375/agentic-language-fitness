## Mechanism and theorem boundary

Perceus transfers counted ownership to a callee instead of necessarily retaining a caller's reference until lexical scope exit. A list map can reclaim consumed input nodes while producing its output. This explains a memory opportunity, subject to sharing and the mapped computation; it does not promise that every map halves process memory.

The optimization sequence inserts `dup`/`drop`, specializes drops when constructor fields are known, pushes duplications into branches, and fuses cancelling operations. Reuse analysis pairs a dead matched object with a later same-sized constructor. A runtime uniqueness check permits overwriting its storage; otherwise the result is allocated separately. Reuse specialization writes only changed fields. Inlining can expose constructor pairs, so source organization affects opportunities. Persistent sharing preserves old versions by copying shared portions; unique portions can still be reused.

Figures 2–3 compare imperative Morris traversal with a functional visitor representation. Visitor constructors can occupy the original tree nodes, and tail calls replace an explicit stack. The stated in-place traversal opportunity assumes unique input, matching node sizes and suitable compilation; allocations or effects of the supplied function remain separate. This is a concrete predecessor for functional source implemented with mutation, not evidence that ordinary F# compilation supplies the same transformations.

Koka makes control flow explicit through its effect compilation. Exceptions require releases on the corresponding paths. Arbitrary foreign nonlocal exits do not follow automatically from the core proof. Objects start thread-local and are recursively marked shared when needed; marking can traverse the reachable graph, and shared objects are never marked local again. Atomic reference operations remain necessary on shared objects. Shared mutable-reference reads also face the load-then-increment versus free race; the paper discusses double-CAS, hazard pointers or locking. The runtime's sticky high-count range deliberately retains an object for the remaining program lifetime. Neither this finite-counter behavior nor a complete concurrent runtime is modeled by the mathematical counters.

Cycles are another explicit boundary: this implementation has no cycle collector, and mutable-reference cycles must be broken by the programmer. The formal heap excludes cycles and mutable references. Reference-count decrements can cascade; the paper supplies no general frame-time or pause bound.

| Formal result | What is established in the stated calculus | Boundary |
| --- | --- | --- |
| Theorem 1; appendix C.1–C.2 | A translated closed source evaluation that terminates has a corresponding reference-counted heap evaluation with the same unfolded result | Strict untyped functional core with explicit control flow; not a proof of every Koka pass, effect translation, foreign interface or concurrent execution |
| Theorem 2; C.3 | Intermediate heap entries remain reachable from the expression containing reference-count instructions | A pending `drop` can itself retain a reference; this property alone does not imply prompt reclamation |
| Theorem 3; C.4 | The syntax-directed algorithm is an instance of the declarative resource calculus | Owned and borrowed environments have explicit disjointness, free-variable and multiplicity invariants |
| Theorem 4; C.5 | After immediate `dup`/`drop` steps, intermediate heap entries are reachable from the expression with reference-count instructions erased | The theorem states a terminating heap-evaluation premise. Reachability is syntactic, not a semantic oracle for future use; it is not a bound on bytes, stack, allocator fragmentation, RSS or latency |

The appendix develops heap resource consumption, extension/drop relationships, simulation, well-formedness preservation and erased-expression reachability. Its well-formed heap definitions explicitly prohibit dependency cycles. Formal borrowing of a surrounding live environment differs from S145's general borrowed function parameters; adding selective function borrowing is future work here and may retain data longer.

Crucially, extended page 11 and published page 12 place the further optimization proofs outside this paper's scope. Thus Perceus supplies a formal account of core reference-count insertion, not a completed proof of S145's compiler or all later reuse optimizations. The paper itself observes that reuse can hold storage longer and increase peak memory. “Garbage free” must not be propagated from the core theorem to an unconditional claim about optimized Koka's physical footprint.

## Measurements and comparators

Figure 9 reports ten-run medians on a six-core AMD 3600XT at 3.8 GHz, 64 GiB memory, Ubuntu 20.04. Koka 2.0.3 generates C compiled by GCC 9.3 with customized mimalloc. Comparators are OCaml 4.08.1, GHC 8.6.5 with strictness annotations, Swift 5.3 translated with loops for tail recursion, Java 15.0.1 with G1, and GCC 9.3 C++ with libc allocation. These bundle language, compiler, representation, allocator and translation choices. The authors frame them as viability evidence rather than an isolated collector comparison. Most workloads descend from S145's Lean suite, not independent new task families.

The following values are transcribed from Figure 9. Each cell is **time / peak RSS**, normalized to optimized Koka **within that workload**; Koka is 1.00 / 1.00 in every row. Lower is better. Separate row normalizers prevent inferring a retained-history penalty by dividing different rows.

Disabling drop/reuse specialization and reuse analysis is a **bundled** ablation. The largest AMD time penalties are 2.45× without retained versions and 1.86× with every fifth tree retained. Shared-expression workloads have smaller time differences. For constant folding, no-opt uses 11% less RSS relative to optimized Koka; equivalently, the rounded ratio makes optimized usage about 12.4% higher relative to no-opt. The authors attribute this to storage held for reuse. OCaml also uses less RSS in two rows, with allocation-eliminating compiler transformations offered as an explanation. These observations are compatible with the theorem's narrower scope.

Figure 11 uses a ten-core Intel i9-7900X at 4.30 GHz and Ubuntu 20.04. Its no-opt time ratios are 2.12, 1.63, 1.04, 0.96 and 1.25 in the same workload order; thus the optimized version is slightly slower on that machine's nqueens row. No-opt RSS is again 1.00 except 0.89 for cfold. C++ rbtree is 1.05× Koka there versus 0.92× on AMD. This is another author machine, not independent replication. The appendix marks C++ checkpoint results with a cross rather than a valid timing/RSS comparison.

C++ is not an equivalent persistent comparator: rbtree mutates `std::map`; deriv, nqueens and cfold do not reclaim their allocations. The paper offers no usable C++ persistent-checkpoint result. Java's high rbtree footprint can reportedly be reduced with slower tuned execution, but the checked script does not specify that heap-tuning experiment. The separate all-atomic experiment reports 5–59% slowdown; it does not establish shared-object prevalence in games or bound concurrent latency. No developer/agent effort, external-effect rollback or interactive game outcome is measured.

## What the named source release resolves and leaves unresolved

The [pinned runner](https://github.com/koka-lang/koka/blob/0d7fb9b09e0c842e948d62b08014ad198de0c040/test/bench/run.kk) measures elapsed time and maximum RSS with `/usr/bin/time`. It iterates workloads and languages in fixed list order, repeats a selected test sequentially, and defaults to one iteration unless overridden. If more than two iterations contain a unique slowest time, it removes that row and averages the remainder, including RSS. Its displayed variability is a standard deviation, not a confidence interval; normalized error calculations do not propagate baseline uncertainty. This disagrees with the paper's ten-run **median** description. No saved invocation/raw trials were recovered from the inspected release to resolve which procedure produced the figures. The mismatch is not a reproduced measurement failure.

The [Koka configuration](https://github.com/koka-lang/koka/blob/0d7fb9b09e0c842e948d62b08014ad198de0c040/test/bench/koka/CMakeLists.txt) corroborates the joint `--fno-parcreuse --fno-parcspec` ablation. The runner applies Java `-Xss128m` specifically for constant folding; this is stack sizing, not the unspecified heap-footprint tuning. The README's CTest instructions and the chart-producing runner are distinct entry points. Exact build/tool versions, emitted code and paper-run binding remain unverified.

Both paper editions say **42 million** rbtree insertions. The inspected Koka and C++ sources specify **4,200,000**, as do Koka/Haskell/OCaml checkpoint variants. The published source-count discrepancy is retained rather than silently corrected. Unshared Koka uses `int32` keys 0 through 4,199,999; its checkpoint variant uses `int` keys 4,200,000 down to 1. Consequently these sources change more than root retention alone.

The checkpoint implementations accumulate one version at each multiple of five plus the final tree: 840,001 list entries for the specified input. Their result folds only the newest tree. This supports a retained-root workload description, not correctness checking of all historical versions or a demonstrated rollback operation. Compiler treatment and exact peak liveness require emitted-code/runtime evidence absent here. The Haskell source makes tree fields and successive trees strict. Its red-node equality branch differs from the other maps, but descending unique input keys do not exercise that branch; the source difference does not establish a failure on the benchmark workload.

The [C++ checkpoint file](https://github.com/koka-lang/koka/blob/0d7fb9b09e0c842e948d62b08014ad198de0c040/test/bench/cpp/rbtree-ck.cpp) is a full-copy attempt with a default of only 4,200 insertions and an explicit nonzero return to mark the test unusable. It supplies neither a structurally shared rival nor evidence that no such C++ implementation is possible. The constant-folding source builds a depth-20 expression, evaluates the original, then reassociates/folds/evaluates it; it prints both values but is not a general equivalence oracle. Its accumulated arithmetic and sharing are specific to that program.

## Consequences and live follow-up

For B04/B06, this work strengthens the positive case that immutable source and efficient runtime mutation can coexist under ownership and compilation conditions. It also makes resource accounting more precise: live historical roots prevent reclamation, delayed reuse can retain extra storage, and a reachability theorem does not rank process footprints across implementations. For B12, the source/paper scale and aggregation discrepancies require explicit edition/run correspondence before treating these figures as reconstructed experiments.

G21 supplies 36 incoming DOI edges/37 nodes at depth 1, cap 150, without truncation or low-coverage flags. All returned titles and supplied contexts were screened. SC85 returns five exact identities at `limit:20`, offset 0; its abstracts are truncated and confer no full-method credit. Repeated G20 and earlier modal-FRP decisions are reused, except frame-limited reuse now advances because a concrete space-bound issue is live. The [runtime screen](../nu-background-runtime-screen-2026-10-01.md) records the new versus reused dispositions and primary routes.

**S149** [frame-limited reuse](https://doi.org/10.1145/3547634) is selected for the direct space-growth counterexample and replacement guarantee; **S150** [Snapshottable Stores](https://doi.org/10.1145/3674637) is selected as an imperative capture/restore alternative. Both have native records and PDFs. FP² remains a conditional stronger static allocation guarantee; concurrent read-reclaim methods remain conditional on a concurrency claim. RRB vectors/iterators, MapReplay, .NET/game transfer, C11 continuation and other survey themes remain open. The bibliography identifies earlier linear-resource, residual-reference-counting, uniqueness and aggregate-update foundations; this note makes no priority claim for Perceus and does not require rereading every foundation to establish its stated boundary.

**Unique:** unconfirmed for Nu, with explicit prior mechanisms for functional source and physical reuse. **Valuable:** favorable scoped time/RSS evidence with sharing, adverse cases and retention costs; net Nu benefit remains unmeasured. **Scientifically valid:** complete extended primary reconstruction and bounded edition/source checks, with optimization-proof and experiment-correspondence limits. No runtime experiment or ISE apparatus is validated. All experimental holds remain.
